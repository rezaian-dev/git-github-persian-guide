<h2><span class="hx"><span class="hx-t">🤔 چرا Git مهارت شغلی است؟</span></span></h2>
<p>در آگهی‌های ۲۰۲۶ تقریباً هیچ نقش نرم‌افزاری بدون Git وجود ندارد. اما شرکت‌های خوب دیگر نمی‌پرسند «تفاوت <code>pull</code> و <code>fetch</code> چیست؟» — مدل ذهنی می‌پرسند:</p>
<blockquote>
<p>«اگر روی <code>main</code> مشترک <code>rebase</code> کنی چه فاجعه‌ای رخ می‌دهد؟»
«چطور یک باگ را با <code>bisect</code> در تاریخچهٔ ده هزار کامیتی پیدا می‌کنی؟»
«Ruleset با Branch Protection چه فرقی دارد؟»</p>
</blockquote>
<p>این کتاب برای همان سطح نوشته شده است.</p>
<div class="callout callout-note"><div class="callout-title">سه قطعه که تا آخر کتاب تکرار می‌شوند</div>
<p class="keep-next">تا فصل ۶ همین‌ها را با مثال می‌بینی. الان فقط معنی‌شان را بدان:</p>
<ol>
<li><strong>کامیت (commit)</strong> — یک عکس ثبت‌شده از <em>همه</em> فایل‌های پروژه در یک لحظه، نه فقط فهرست خطوط عوض‌شده.</li>
<li><strong>شاخه (branch)</strong> — یک برچسب روی یک کامیت. پوشه را کپی نمی‌کند؛ فقط می‌گوید «الان این عکس، نوک کار ماست».</li>
<li><strong>سه درخت</strong> — (الف) فایل‌هایی که در ادیتور می‌بینی، (ب) پیش‌نویس کامیت بعدی، (ج) آخرین عکس ثبت‌شده.</li>
</ol>
<p>هر فرمان Git فقط یکی از این‌ها را عوض می‌کند. وقتی بپرسی «این فرمان کدام را عوض کرد؟» دیگر مبهم نمی‌ماند.</p>
</div>
<h2><span class="hx"><span class="hx-t">📖 تاریخچه — از BitKeeper تا Git ۳.۰</span></span></h2>
<ul>
<li><strong>۲۰۰۵:</strong> لینوس توروالدز Git را در دو هفته ساخت؛ هستهٔ لینوکس دیگر نمی‌توانست به BitKeeper تکیه کند.</li>
<li><strong>۲۰۰۸:</strong> GitHub متولد شد و «اجتماع روی کد» را ساخت؛ Fork و Pull Request زبان مشترک صنعت شد.</li>
<li><strong>۲۰۱۹:</strong> <code>git switch</code> و <code>git restore</code> آمدند تا <code>checkout</code> دوچهره را بشکنند.</li>
<li><strong>۲۰۲۵ (Git ۲.۵۱):</strong> <code>switch</code> و <code>restore</code> دیگر آزمایشی نیستند؛ reftable و SHA-256 برای مخازن جدید آماده‌اند.</li>
<li><strong>۲۰۲۶:</strong> Git ۳.۰ در افق است — پاکسازی فرمان‌های قدیمی، hash پیش‌فرض SHA-256، و backend سریع‌تر برای میلیون‌ها ref.</li>
<li><strong>گیت‌هاب ۲۰۲۵–۲۰۲۶:</strong> Rulesets، Immutable Releases، Copilot Coding Agent، Agent HQ، و Actions تو در تو.</li>
</ul>
<div class="callout callout-tip"><div class="callout-title">دو مسیر در هر فصل — هیچ‌کدام را حذف نمی‌کنیم</div>
<p>برای عوض کردن شاخه <strong>هرگز</strong> <code>checkout</code> نمی‌نویسیم: <strong><code>git switch</code> شاخه، <code>git restore</code> فایل.</strong></p>
<p>هر مهارت را دو بار می‌بینی: فرمان در <strong>ترمینال</strong> و دکمه در <strong>VS Code</strong> (پنل Source Control و افزونهٔ GitHub Pull Requests). مفهوم را در ترمینال بفهم؛ کار روزانه را در VS Code انجام بده.</p>
</div>

<h3><span class="hx"><span class="hx-t">۱. فرمان را حفظ نکن — بپرس کدام لایه عوض شد</span></span></h3>
<p>بعد از هر فرمان از خودت بپرس: فایل روی دیسک عوض شد، پیش‌نویس کامیت عوض شد، یا تاریخچهٔ ثبت‌شده؟ (اسامی دقیق این سه لایه در فصل ۳ است.)</p>
<h3><span class="hx"><span class="hx-t">۲. ترمینال و VS Code را با هم یاد بگیر</span></span></h3>
<p>تقریباً هر کار دو شکل دارد: یک فرمان و یک دکمه. اگر فقط یکی را بلد باشی، در تیم گیر می‌کنی.</p>
<h3><span class="hx"><span class="hx-t">۳. عمداً خراب کن — برگشت دارد</span></span></h3>
<p class="keep-next">حذف تاریخچهٔ ثبت‌شده سخت است، ولی حرکت اشتباه HEAD معمولاً تا حدود ۹۰ روز در <code>reflog</code> مانده. فصل ۸ دقیقاً می‌گوید کدام Undo کدام لایه را لمس می‌کند.</p>

01

معرفی Git و نقشه راه ۲۰۲۶ — از صفر تا Senior

Git ابزار ثبت تاریخچهٔ کد است؛ هر کامیت یک عکس کامل از پروژه در آن لحظه است. VS Code و GitHub ظاهر این ابزارند — مغز کار همان Git روی رایانهٔ توست.

🎯 اهداف یادگیری این فصل

بعد از این فصل، بدون ابهام می‌توانی بگویی:

  • Git چیست (برنامه روی رایانهٔ تو) و GitHub چیست (سایت میزبانی)
  • چرا به‌جای کپی‌کردن پوشه، از Git استفاده می‌کنیم
  • کامیت، شاخه و «عکس لحظه‌ای» یعنی چه
  • این کتاب را با چه ترتیبی بخوانی

🤔 چرا Git مهارت شغلی است؟

در آگهی‌های ۲۰۲۶ تقریباً هیچ نقش نرم‌افزاری بدون Git وجود ندارد. اما شرکت‌های خوب دیگر نمی‌پرسند «تفاوت pull و fetch چیست؟» — مدل ذهنی می‌پرسند:

«اگر روی main مشترک rebase کنی چه فاجعه‌ای رخ می‌دهد؟» «چطور یک باگ را با bisect در تاریخچهٔ ده هزار کامیتی پیدا می‌کنی؟» «Ruleset با Branch Protection چه فرقی دارد؟»

این کتاب برای همان سطح نوشته شده است.

سه قطعه که تا آخر کتاب تکرار می‌شوند

تا فصل ۶ همین‌ها را با مثال می‌بینی. الان فقط معنی‌شان را بدان:

  1. کامیت (commit) — یک عکس ثبت‌شده از همه فایل‌های پروژه در یک لحظه، نه فقط فهرست خطوط عوض‌شده.
  2. شاخه (branch) — یک برچسب روی یک کامیت. پوشه را کپی نمی‌کند؛ فقط می‌گوید «الان این عکس، نوک کار ماست».
  3. سه درخت — (الف) فایل‌هایی که در ادیتور می‌بینی، (ب) پیش‌نویس کامیت بعدی، (ج) آخرین عکس ثبت‌شده.

هر فرمان Git فقط یکی از این‌ها را عوض می‌کند. وقتی بپرسی «این فرمان کدام را عوض کرد؟» دیگر مبهم نمی‌ماند.

📖 تاریخچه — از BitKeeper تا Git ۳.۰

  • ۲۰۰۵: لینوس توروالدز Git را در دو هفته ساخت؛ هستهٔ لینوکس دیگر نمی‌توانست به BitKeeper تکیه کند.
  • ۲۰۰۸: GitHub متولد شد و «اجتماع روی کد» را ساخت؛ Fork و Pull Request زبان مشترک صنعت شد.
  • ۲۰۱۹: git switch و git restore آمدند تا checkout دوچهره را بشکنند.
  • ۲۰۲۵ (Git ۲.۵۱): switch و restore دیگر آزمایشی نیستند؛ reftable و SHA-256 برای مخازن جدید آماده‌اند.
  • ۲۰۲۶: Git ۳.۰ در افق است — پاکسازی فرمان‌های قدیمی، hash پیش‌فرض SHA-256، و backend سریع‌تر برای میلیون‌ها ref.
  • گیت‌هاب ۲۰۲۵–۲۰۲۶: Rulesets، Immutable Releases، Copilot Coding Agent، Agent HQ، و Actions تو در تو.
دو مسیر در هر فصل — هیچ‌کدام را حذف نمی‌کنیم

برای عوض کردن شاخه هرگز checkout نمی‌نویسیم: git switch شاخه، git restore فایل.

هر مهارت را دو بار می‌بینی: فرمان در ترمینال و دکمه در VS Code (پنل Source Control و افزونهٔ GitHub Pull Requests). مفهوم را در ترمینال بفهم؛ کار روزانه را در VS Code انجام بده.

🔬 Git چه چیزی نیست؟

تصور غلط واقعیت روشن
Git همان GitHub است Git برنامهٔ روی رایانهٔ توست. GitHub فقط یکی از سایت‌های میزبان است (GitLab و Gitea هم هستند). بدون اینترنت هم Git کار می‌کند.
Git فقط پشتیبان فایل است Git علاوه بر فایل، چرا عوض شد (پیام کامیت) و چه کسی / کی را هم نگه می‌دارد.
شاخه = کپی کل پروژه شاخه یک برچسب کوتاه روی یک کامیت است؛ ساختنش آنی است و پوشه را دوبرابر نمی‌کند.
کامیت = فقط diff کامیت یک snapshot است: عکس کامل درخت فایل‌ها در آن لحظه. Diff بعداً از مقایسهٔ دو عکس به‌دست می‌آید.

شکل ۱ — هر دایره یک کامیت است. پیکان به کامیت قبلی (والد) می‌رود. حلقه وجود ندارد؛ به این گراف DAG می‌گویند. شاخه فقط نام روی یکی از دایره‌هاست.

DAG یعنی Directed Acyclic Graph: گراف جهت‌دار بدون دور. اگر این یک جمله را حفظ کنی، merge (دو والد) و rebase (گره‌های جدید) دیگر رمز نیستند.

🗺️ اکوسیستم ۲۰۲۶ — چه چیزی یاد بگیریم؟

🧠 چگونه این کتاب را بخوانیم؟

۱. فرمان را حفظ نکن — بپرس کدام لایه عوض شد

بعد از هر فرمان از خودت بپرس: فایل روی دیسک عوض شد، پیش‌نویس کامیت عوض شد، یا تاریخچهٔ ثبت‌شده؟ (اسامی دقیق این سه لایه در فصل ۳ است.)

۲. ترمینال و VS Code را با هم یاد بگیر

تقریباً هر کار دو شکل دارد: یک فرمان و یک دکمه. اگر فقط یکی را بلد باشی، در تیم گیر می‌کنی.

۳. عمداً خراب کن — برگشت دارد

حذف تاریخچهٔ ثبت‌شده سخت است، ولی حرکت اشتباه HEAD معمولاً تا حدود ۹۰ روز در reflog مانده. فصل ۸ دقیقاً می‌گوید کدام Undo کدام لایه را لمس می‌کند.

📘 مسیر پیشنهادی

هفته ۱: فصل ۱–۱۰ — مدل ذهنی + Source Control از صفر (Ctrl+Shift+G)
هفته ۲: فصل ۱۱–۲۲ — همکاری واقعی روی GitHub
هفته ۳: فصل ۲۳–۳۲ — rebase، Actions، امنیت
هفته ۴: فصل ۳۳–۳۶ — کارگاه، اشتباهات، مصاحبه

🚀 چک‌لیست فهم عمیق
  • می‌توانی مدل را روی کاغذ بکشی؟
  • می‌توانی همان کار را در VS Code انجام دهی؟
  • می‌توانی بگویی کدام فرمان تاریخچه را بازنویسی می‌کند؟
  • می‌توانی در مصاحبه ۲ دقیقه توضیح دهی؟
سؤالات مصاحبه (با پاسخ)

Junior — Git و GitHub چه فرقی دارند؟ Git موتور نسخه‌بندی توزیع‌شده روی ماشین توست. GitHub سرویس میزبانی، PR، Issue، Actions و هویت تیمی است.

Mid — چرا Git معمولاً از SVN سریع‌تر حس می‌شود؟ چون کل تاریخچه روی رایانهٔ توست و هر فایل با هش محتوایش شناخته می‌شود. شبکه فقط وقتی لازم است که بخواهی با دیگران همگام شوی — نه برای هر مقایسه.

Senior — DAG یعنی چه و چرا مهم است؟ تاریخچه یک خط نیست؛ یک گراف است. Merge کامیتی با دو والد می‌سازد. Rebase کامیت‌های جدید می‌سازد (هش عوض می‌شود). اگر گراف را ببینی، می‌فهمی چرا force-push روی main کار دیگران را می‌شکند.

✅ جمع‌بندی و اتصال

  • Git روی رایانهٔ تو تاریخچه را با عکس لحظه‌ای و برچسب شاخه نگه می‌دارد.
  • GitHub میزبان + صفحهٔ PR + قوانین تیم + اجرای خودکار تست است.
  • مسیر این کتاب: switch/restore، VS Code، بعد GitHub، بعد امنیت و CI.

فصل بعد: نصب Git، نام و ایمیل، کلید SSH و امضای کامیت — تا هویت تو در تاریخچه درست ثبت شود.

02

نصب و هویت — ستاپ حرفه‌ای Git در ۲۰۲۶

هر کامیت نام و ایمیل را داخل خودش ذخیره می‌کند. اگر این دو را غلط بگذاری، تاریخچه مال کس دیگری به نظر می‌رسد. این فصل را یک‌بار درست تنظیم کن.

🎯 اهداف یادگیری

  • Git را روی Windows / macOS / Linux نصب و نسخه را چک کنی
  • user.name و user.email را درست — و ترجیحاً محلی — تنظیم کنی
  • SSH Key بسازی، به GitHub اضافه کنی و با gh auth وارد شوی
  • کامیت‌ها را با SSH sign کنی (جایگزین مدرن GPG)

🛠️ نصب Git ۲.۵۱+

نصب — لینوکس / macOS / Windows
# Debian / Ubuntu
sudo apt update && sudo apt install -y git gh

# macOS
brew install git gh

# Windows (پاورشل به‌عنوان Admin)
winget install Git.Git GitHub.cli

git --version    # باید ۲.۵۱ یا جدیدتر باشد
gh --version

در VS Code: از Command Palette (Ctrl+Shift+P) بنویس Git: Show Git Output. اگر Git پیدا نشود، مسیر را در git.path تنظیم کن.

🪪 هویت — دو لایه

دو هویت جدا وجود دارد و باید یکی باشند:

  1. هویت Git — همان user.name و user.email که داخل هر کامیت نوشته می‌شود.
  2. حساب GitHub — ایمیلی که در Settings گیت‌هاب ثبت کرده‌ای.

اگر ایمیل کامیت با ایمیل حساب یکی نباشد، کنار کامیت در GitHub آواتار خاکستری می‌بینی و نشان Verified (تأیید امضا) نمی‌آید.

پیکربندی هویت
# سراسری — فقط اگر یک هویت داری
git config --global user.name "rezaian-dev"
git config --global user.email "mrezaian.dev@gmail.com"

# بهتر: هویت داخل هر مخزن (توصیهٔ تیمی)
git config user.name "rezaian-dev"
git config user.email "mrezaian.dev@gmail.com"

git config --global init.defaultBranch main
git config --global pull.rebase false
git config --global fetch.prune true
git config --global rerere.enabled true
git config --global core.editor "code --wait"
git config --global alias.st status
git config --global alias.lg "log --oneline --graph --decorate --all"
ایمیل مخفی GitHub

اگر نمی‌خواهی ایمیلت در تاریخچهٔ عمومی دیده شود، از noreply گیت‌هاب استفاده کن:

12345678+rezaian-dev@users.noreply.github.com

در Settings → Emails گزینهٔ Block command line pushes that expose my email را روشن کن.

🔑 SSH — درِ جلویی GitHub

HTTPS با token کار می‌کند اما SSH برای کار روزانه تمیزتر است.

ساخت کلید Ed25519
ssh-keygen -t ed25519 -C "mrezaian.dev@gmail.com"
# Enter — passphrase قوی بگذار

eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519

# کلید عمومی را کپی کن
cat ~/.ssh/id_ed25519.pub

در GitHub: Settings → SSH and GPG keys → New SSH key. بعد:

تست اتصال
ssh -T git@github.com
# Hi rezaian-dev! You've successfully authenticated...

در VS Code وقتی Clone می‌کنی، اگر remote با git@github.com: شروع شود از همین کلید استفاده می‌شود.

✍️ امضای کامیت با SSH — استاندارد ۲۰۲۶

GPG هنوز معتبر است اما SSH signing ساده‌تر است و همان کلید را دوباره مصرف می‌کند.

فعال‌سازی امضا
git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global commit.gpgsign true
git config --global tag.gpgsign true

همان کلید عمومی را در GitHub به‌عنوان Signing Key هم اضافه کن. بعد از آن، کامیت‌هایت نشان Verified می‌گیرند.

VS Code

در Settings بگذار:

git.enableCommitSigning: true

دکمهٔ Commit از همین تنظیم پیروی می‌کند — لازم نیست هر بار پرچم -S بزنی.

🐙 ورود با GitHub CLI

gh auth
gh auth login
# GitHub.com → SSH → Login with browser

gh auth status
gh api user --jq .login    # rezaian-dev

از این به بعد gh repo create، gh pr create و gh run list بدون token دستی کار می‌کنند.

سؤالات مصاحبه (با پاسخ)

Junior — چرا SSH بهتر از HTTPS است؟ کلید روی دیسک می‌ماند، passphrase در agent کش می‌شود، و token PAT را هر چند ماه عوض نمی‌کنی.

03

سه درخت — Working Tree، Index و Repository

Git فایل‌ها را هم‌زمان در سه جا نگه می‌دارد: آنچه در ادیتور می‌بینی، پیش‌نویس کامیت بعدی، و آخرین عکس ثبت‌شده. اگر این سه را قاطی کنی، reset و Save و Commit برایت یکی به نظر می‌رسند.

🎯 اهداف یادگیری

  • سه درخت را نام ببری و نقش هر کدام را بکشی
  • وضعیت فایل را در VS Code بخوانی: U، M، A، D
  • تفاوت unstaged و staged را با مثال نشان دهی
  • بگویی add، restore و commit دقیقاً چه چیزی را کپی می‌کنند

🧠 مدل ذهنی

Git فایل‌ها را در سه لایه نگه می‌دارد:

  1. Working Tree — فایل‌هایی که در Explorer می‌بینی و با Save ذخیره می‌کنی. هنوز تاریخچه نیست.
  2. Index (Staging Area) — پیش‌نویس کامیت بعدی. git add یا دکمهٔ Stage فایل را از دیسک به این پیش‌نویس کپی می‌کند.
  3. Repository (HEAD) — آخرین عکس ثبت‌شده. فقط commit این لایه را جلو می‌برد.

شکل ۲ — add از Working به Index می‌رود؛ commit از Index یک شیء commit می‌سازد.

فرمول طلایی

status = diff(Working, Index) + diff(Index, HEAD)

دو ستون تغییرات در VS Code دقیقاً همین دو diff هستند.

🔍 خواندن git status

وضعیت را با چشم مسلح ببین
git status -sb
# ## main
#  M src/auth.ts      # فاصله + M یعنی تغییر در Working، هنوز stage نشده
# M  src/api.ts       # M در ستون اول یعنی staged
# MM README.md        # هم staged هم بعدش دوباره ویرایش شده
# ?? notes.txt        # untracked — Git اصلاً نمی‌شناسدش

در VS Code همین اطلاعات چنین دیده می‌شود:

نشانه معنی اقدام
U Untracked Stage یا به .gitignore بسپار
M Modified Stage / Discard
A Added فایل جدید staged
D Deleted حذف staged یا بازیابی
C Conflict Resolve در ادیتور

🧪 آزمایش ۳۰ ثانیه‌ای

سه درخت را حس کن
echo "v1" > hello.txt
git add hello.txt          # Working = Index  (هر دو v1)  HEAD هنوز ندارد
git commit -m "v1"         # هر سه = v1

echo "v2" > hello.txt      # Working=v2  Index=v1  HEAD=v1
git add hello.txt          # Working=v2  Index=v2  HEAD=v1
git commit -m "v2"         # هر سه = v2

حالا می‌فهمی چرا «کامیت نکردم ولی Save کردم» تاریخچه را عوض نمی‌کند — Save فقط Working Tree است.

🎛️ فرمان‌ها روی کدام درخت؟

فرمان Working Index Repo
ویرایش در VS Code / Save ✓
git add / Stage ✓
git commit ✓
git restore file ✓
git restore --staged ✓
git reset --soft ✓ (HEAD حرکت)
git reset --mixed ✓ ✓
git reset --hard ✓ ✓ ✓
reset --hard

--hard هر سه درخت را با کامیت هدف یکی می‌کند و تغییرات ذخیره‌نشده را می‌کشد. در VS Code معادل Discard All Changes + حرکت HEAD است. تا فصل ۸ بدون تور ایمنی (reflog) نزدیکش نشو.

🖼️ در VS Code کجایند این درخت‌ها؟

  • Explorer = Working Tree
  • Source Control → Changes = diff(Working, Index)
  • Source Control → Staged Changes = diff(Index, HEAD)
  • Timeline / Git Graph = Repository

وقتی فایلی را Stage می‌کنی، از لیست Changes به Staged می‌پرد — یعنی کپی snapshot آن فایل به Index.

عادت Senior

git add -p یا Stage انتخابی در VS Code (روی hunk). کامیت را مثل پاراگراف می‌نویسی نه مثل سطل زباله.

عادت Junior

git add . کورکورانه. فایل env، آرتیفکت بیلد و رمز داخل کامیت می‌رود.

سؤالات مصاحبه (با پاسخ)

Junior — Staging یعنی چه؟ سبد خرید قبل از پرداخت. commit پرداخت است.

Mid — چرا Index وجود دارد؟ تا یک Working شلوغ را به چند کامیت معنادار بشکنی.

Senior — Index از نظر داده چیست؟ یک درخت مرتب‌شده از cache entryها (مسیر، mode، OID، stat) که commit آن را به یک tree object تبدیل می‌کند.

✅ چک‌لیست فهم

  • سه درخت را بدون نگاه به کتاب نام می‌بری
  • M در ستون اول و دوم status -sb را بلدی
  • می‌دانی Save ≠ Commit
  • Stage انتخابی را به add . ترجیح می‌دهی

04

اولین مخزن — init تا log

در این فصل یک پوشه را به مخزن Git تبدیل می‌کنی، دو کامیت با پیام روشن می‌نویسی، و با log می‌بینی تاریخچه دقیقاً چه شکلی شده.

🎯 اهداف یادگیری

  • مخزن را از صفر با git init یا از VS Code بسازی
  • پیام کامیت خوب بنویسی
  • log را با گراف بخوانی
  • تفاوت --allow-empty و کامیت واقعی را بدانی

🚀 ساخت مخزن

روش ۱ — ترمینال (پایه)

init تمیز
mkdir git-lab && cd git-lab
git init -b main
# Initialized empty Git repository in .../.git/

echo "# Git Lab" > README.md
git add README.md
git status
git commit -m "chore: bootstrap repository"

پرچم -b main شاخهٔ پیش‌فرض را master نمی‌گذارد. اگر فراموش کردی: git config --global init.defaultBranch main.

روش ۲ — VS Code (توصیهٔ این کتاب)

  1. پوشه را با File → Open Folder باز کن
  2. نوار کناری آیکون Git را بزن (Ctrl+Shift+G)
  3. دکمهٔ Initialize Repository
  4. فایل بساز، در Changes ظاهر می‌شود
  5. پیام را بنویس و Ctrl+Enter

اگر پنل خالی دیدی و دکمهٔ Initialize نبود، یا پوشه Git ندارد یا Git در PATH نیست.

✍️ پیام کامیت — قرارداد این کتاب

از Conventional Commits استفاده می‌کنیم (فصل ۲۲ عمیق می‌شود):

قالب
type(scope): summary

بدنهٔ اختیاری — چرا، نه چه.

انواع رایج: feat، fix، docs، chore، refactor، test، ci.

خوب

feat(auth): add refresh-token rotation

چرا: نوع + محدوده + فعل امری + نتیجه.

بد

update یا fix bug یا asdf

تاریخچهٔ بی‌معنی، git log را به زباله‌دان تبدیل می‌کند.

در VS Code پیام را در جعبهٔ بالا می‌نویسی. Ctrl+Enter کامیت می‌کند. اگر Smart Commit روشن باشد و چیزی stage نشده باشد، همه چیز را قورت می‌دهد — در فصل ۲ آن را خاموش کردیم.

📜 خواندن تاریخچه

log به سبک Senior
git log --oneline --decorate --graph --all
git log -1 -p                 # آخرین کامیت + diff
git show HEAD                 # معادل بالا
git log --author="rezaian" --since="2 weeks ago"
git shortlog -sn              # چه کسی چقدر کامیت کرده

در VS Code:

  • Timeline زیر فایل → تاریخچهٔ همان فایل
  • Git Graph / GitLens → کل DAG
  • کلیک روی کامیت در Source Control → جزئیات

🔬 داخل .git چه خبر است؟

تور سریع
ls .git
# HEAD  config  description  hooks  info  objects  refs

cat .git/HEAD          # ref: refs/heads/main
cat .git/refs/heads/main
# 9f3a1c...  ← هش کامیت فعلی

هنوز لازم نیست packfile را بفهمی (فصل ۳۰). فقط بدان: هر چیز ماندگار اینجاست؛ پاک کردن .git یعنی قتل تاریخچه.

amend برای ۵ دقیقهٔ اول

اگر همین الان پیام را غلط نوشتی و هنوز push نکرده‌ای:

git commit --amend -m "docs: fix readme title"

در VS Code: تیک Amend کنار دکمهٔ Commit (منوی کشویی ✓).

هرگز amend بعد از push

--amend هش را عوض می‌کند. اگر دیگران آن کامیت را گرفته‌اند، تاریخچه دوپاره می‌شود. قانون: فقط کامیت محلیِ pushنشده.

سؤالات مصاحبه (با پاسخ)

Junior — git init چه می‌سازد؟ پوشهٔ .git با HEAD، objects، refs و config.

Mid — چرا پیام امری می‌نویسیم؟ کامیت را مثل وصله بخوان: «این وصله refresh-token را اضافه می‌کند.» نه «اضافه کردم.»

Senior — تفاوت git log -p و git show؟ show یک شیء را نمایش می‌دهد؛ log -p پیمایش تاریخچه با diff هر کامیت است.

✅ چک‌لیست فهم

  • مخزن با شاخهٔ main ساخته‌ای
  • حداقل دو کامیت Conventional داری
  • git lg (یا alias) گراف را نشان می‌دهد
  • می‌دانی .git قلب مخزن است

فصل بعد: اشیای Git — blob، tree، commit و جادوی hash.

05

اشیای Git — blob، tree، commit و hash

Git هر فایل و هر کامیت را با یک اثرانگشت (هش) می‌شناسد. اگر حتی یک حرف پیام کامیت عوض شود، اثرانگشت عوض می‌شود — برای همین «ویرایش تاریخچه» در واقع ساختن کامیت جدید است، نه دستکاری فایل قدیمی.

🎯 اهداف یادگیری

  • چهار نوع شیء را نام ببری: blob، tree، commit، tag
  • توضیح دهی چرا بازنویسی کامیت هش را عوض می‌کند
  • با cat-file و rev-parse یک کامیت را کالبدشکافی کنی
  • تفاوت SHA-1 و SHA-256 (مسیر Git ۳.۰) را بدانی

🧠 محتوا آدرس‌دهی

hash("blob " + size + "\0" + content)  →  شناسهٔ فایل

اگر یک بیت عوض شود، شناسه عوض می‌شود. دو فایل یکسان در کل تاریخچه یک blobاند — این است دلیل ارزان بودن شاخه و سریع بودن Git.

شکل ۳ — commit به tree اشاره می‌کند؛ tree به blobها و treeهای فرزند.

🔬 کالبدشکافی یک کامیت

از HEAD تا بایت‌های فایل
git rev-parse HEAD
git cat-file -p HEAD
git cat-file -p 'HEAD^{tree}'      # در zsh حتماً نقل‌قول بگذار
git ls-tree -r HEAD

خروجی commit شبیه این است:

آناتومی commit
tree 4c2e9a...
parent a91b77...
author rezaian-dev <mrezaian.dev@gmail.com> 1757400000 +0330
committer rezaian-dev <mrezaian.dev@gmail.com> 1757400000 +0330

feat(auth): add refresh-token rotation

چهار چیز هویت کامیت را می‌سازند: tree، والد(ها)، هویت نویسنده/زمان، پیام. --amend روی هر کدام دست بگذارد، هش جدید است.

🏷️ annotated tag

تگ سبک در برابر تگ کامل
git tag v1.0.0                     # سبک: فقط یک ref
git tag -a v1.0.0 -m "release"     # شیء tag با امضا و پیام
git cat-file -p v1.0.0

برای انتشار محصول همیشه annotated (و در فصل ۲۶ امضاشده) بساز.

🧮 SHA-1 در برابر SHA-256

SHA-1 (میراث) SHA-256 (آینده)
طول ۴۰ hex ۶۴ hex
وضعیت ۲۰۲۶ هنوز پیش‌فرض بسیاری از hostها در Git ۲.۵۱+ برای مخزن جدید آماده
GitHub پشتیبانی کامل در حال گسترش — قبل از مهاجرت چک کن
آزمایش — git init --object-format=sha256
مهاجرت عجولانه نکن

مخزن SHA-256 را نمی‌توانی به ریموت SHA-1 پوش کنی. تا وقتی GitHub/تیم تو آماده نشده، روی SHA-1 بمان و فقط مفهوم را بدان.

Reftable (git init --ref-format=reftable) لایهٔ refs را سریع می‌کند، نه hash را. برای monorepoهای عظیم مفید است.

کوتاه‌هش

Git معمولاً ۷–۱۲ کاراکتر اول را می‌پذیرد (9f3a1c). در مخازن خیلی بزرگ ممکن است مبهم شود؛ core.abbrev را بالا ببر یا هش کامل را در اسکریپت‌ها استفاده کن.

سؤالات مصاحبه (با پاسخ)

Junior — blob چیست؟ محتوای فایل، بدون نام. نام در tree ذخیره می‌شود.

Mid — چرا rename در Git «تشخیص» است نه شیء؟ چون blob همان است؛ tree فقط مسیر را عوض کرده. git log --follow این جابه‌جایی را حدس می‌زند.

Senior — commit تغییرناپذیر است یعنی چه؟ شیء در objects دیتابیس هرگز ویرایش نمی‌شود. «ویرایش تاریخچه» یعنی ساختن اشیای جدید و حرکت دادن اشاره‌گر شاخه.

✅ چک‌لیست فهم

  • چهار نوع شیء را بلدی
  • cat-file -p HEAD را تفسیر می‌کنی
  • می‌دانی amend چرا هش را عوض می‌کند
  • SHA-256 را با احتیاط می‌شناسی

فصل بعد: شاخه — ارزان‌ترین اشاره در مهندسی نرم‌افزار.

06

شاخه‌ها — اشاره‌گر، نه کپی

شاخه کپی پروژه نیست. یک فایل کوچک داخل .git/refs/heads/ است که فقط هش یک کامیت را نگه می‌دارد (حدود ۴۰ کاراکتر). ساختن شاخه یعنی نوشتن همین فایل.

🎯 اهداف یادگیری

  • شاخه را به‌عنوان اشاره‌گر به یک commit توضیح دهی
  • با switch و switch -c کار کنی
  • HEAD detached را تشخیص و نجات دهی
  • قرارداد نام‌گذاری تیم را رعایت کنی

🧠 شاخه چیست؟

مسیر refs/heads/main فقط هش کامیت نوک شاخه را نگه می‌دارد. ساخت شاخه = نوشتن یک فایل جدید با یک هش. عوض کردن شاخه = عوض کردن اینکه HEAD به کدام فایل اشاره کند.

شکل ۴ — HEAD به شاخه اشاره می‌کند؛ شاخه به کامیت. وقتی کامیت می‌کنی، هر دو جلو می‌روند.

اشاره‌گرها را ببین
git branch -vv                 # شاخه‌های محلی + tracking
git show-ref --heads
cat .git/HEAD                  # ref: refs/heads/main

🔀 ساخت و تعویض — مسیر مدرن

🖥️ VS Code Git
  1. روی نام شاخه در نوار وضعیت (پایین-چپ) کلیک کن
  2. Create new branch from... → feat/auth
  3. برای برگشت: همان منو → main
  4. Palette: Git: Create Branch / Git: Checkout to...
  5. Publish Branch وقتی آمادهٔ remote شدی
⌨️ Terminal

git switch -c feat/auth

git switch main

git switch -

git branch -d feat/auth فقط اگر merge شده؛ وگرنه Git رد می‌کند.

git branch -D feat/old حذف اجباری

شکل ۴ب — کلیک روی نام شاخه در نوار وضعیت: تعویض، ساخت شاخهٔ جدید، Publish.

شکل ۴پ — Ctrl+Shift+P سپس Git: Create Branch from... معادل git switch -c.

چرا دیگر checkout نه؟

checkout هم شاخه عوض می‌کرد هم فایل برمی‌گرداند. دو معنا = دو برابر باگ انسانی. از Git ۲.۵۱ فرمان‌های switch و restore پایدار و توصیه‌شده‌اند.

📛 نام‌گذاری

پیشوند استفاده مثال
feat/ قابلیت جدید feat/jwt-refresh
fix/ باگ fix/token-expiry
chore/ ابزار / وابستگی chore/bump-actions
hotfix/ تعمیر تولید hotfix/500-login
release/ آماده‌سازی نسخه release/1.4.0

از فاصله، اموجی و نام‌های خیلی کلی (update, ali) پرهیز کن. GitHub شاخه را در URL می‌گذارد.

🪂 HEAD detached — وحشت بی‌مورد

وقتی مستقیم روی یک کامیت checkout/switch کنی (نه روی شاخه)، HEAD به هش می‌چسبد نه به ref.

نجات کارهای detached
git switch --detach HEAD~3     # حداقل ۴ کامیت لازم است
git switch -c rescue
git switch main

در VS Code اگر Graph را بزنی و یک کامیت قدیمی را Checkout کنی، بنر زرد detached HEAD می‌آید. فوری شاخه بساز.

شاخهٔ منتشرشده را بازنویسی نکن

main و شاخه‌هایی که دیگران track می‌کنند مقدس‌اند. بازنویسی یعنی force-push و درد تیم. قانون را در فصل ۲۳ با گوشت و پوست حس می‌کنی.

🌳 دیدن همه چیز

نقشه
git branch -a                  # محلی + remote
git log --oneline --graph --decorate --all

در VS Code افزونهٔ Graph همین نقشه را رنگی می‌کشد — فصل ۱۱ کامل روی آن کار می‌کنیم.

سؤالات مصاحبه (با پاسخ)

Junior — ساخت شاخه فایل‌ها را کپی می‌کند؟ خیر. فقط یک اشاره‌گر جدید.

Mid — تفاوت branch و tag؟ هر دو اشاره‌گرند؛ شاخه با هر commit حرکت می‌کند، تگ معمولاً ثابت می‌ماند.

Senior — HEAD symbolic چیست؟ فایل HEAD معمولاً ref: refs/heads/main است نه خود هش. Detached یعنی HEAD مستقیم هش را نگه می‌دارد.

✅ چک‌لیست فهم

  • شاخه را فایل اشاره‌گر می‌دانی نه پوشه
  • switch -c را به‌جای checkout استفاده می‌کنی
  • از detached بدون وحشت خارج می‌شوی
  • نام شاخه Conventional است

فصل بعد: ادغام — وقتی دو تاریخچه باید یکی شوند.

07

ادغام — fast-forward، merge commit و تعارض

Merge یعنی دو خط تاریخچه را یکی کنی. اگر هر دو خط همان خطوط فایل را جور دیگری عوض کرده باشند، Git نمی‌داند کدام درست است — به آن تعارض می‌گویند و باید خودت انتخاب کنی.

🎯 اهداف یادگیری

  • fast-forward را از merge commit تشخیص دهی
  • تعارض را در VS Code با دکمه‌های Accept حل کنی
  • --no-ff و --squash را بدانی کی استفاده کنی
  • abort کنی وقتی اوضاع خراب شد

🧬 سه شکل ادغام

سناریوی آموزشی
git switch main
git merge feat/auth
نوع کی رخ می‌دهد نتیجه
Fast-forward از وقتی شاخه را ساختی، main هیچ کامیت جدیدی نگرفته Git فقط برچسب main را روی همان کامیت‌های شاخه جلو می‌کشد؛ کامیت ادغام ساخته نمی‌شود
Merge commit هر دو طرف بعد از جدایی کامیت جدید دارند یک کامیت جدید با دو والد ساخته می‌شود
Squash merge معمولاً دکمهٔ GitHub همهٔ کامیت‌های شاخه در یک کامیت روی هدف خلاصه می‌شوند؛ جزئیات میانی در main نمی‌ماند

شکل ۵ — merge تاریخچه را حفظ می‌کند؛ rebase آن را خطی می‌کند (جزئیات در فصل ۲۳).

GitHub و --no-ff

بسیاری از تیم‌ها Create a merge commit را می‌خواهند تا هر PR یک گره قابل‌ردیابی داشته باشد. معادل محلی: git merge --no-ff feat/auth.

💥 تعارض — آناتومی

تعارض وقتی است که Git نمی‌تواند دو تغییر روی یک hunk را ترکیب کند.

نشانه‌های تعارض در فایل
<<<<<<< HEAD
return token;
=======
return rotate(token);
>>>>>>> feat/auth

سه نسخه در ذهن داشته باش:

  • Ours / Current = شاخه‌ای که روی آن هستی (HEAD)
  • Theirs / Incoming = شاخه‌ای که merge می‌کنی
  • Base = جد مشترک (برای merge سه‌طرفه)

شکل ۶ — CodeLens: Accept Current، Accept Incoming، Accept Both، Compare Changes.

مسیر حل در VS Code

  1. Source Control بخش Merge Changes را نشان می‌دهد
  2. فایل را باز کن — نوار CodeLens بالای تعارض
  3. انتخاب کن یا دستی ویرایش کن
  4. فایل را Stage کن (علامت تعارض تمام می‌شود)
  5. Commit ادغام را کامل می‌کند
ترمینال هم‌ارز
git merge --abort              # پشیمانی قبل از commit
git merge --continue           # بعد از حل
git diff --name-only --diff-filter=U
Accept Both کورکورانه

هر دو را پذیرفتن گاهی کد syntactically درست و semantically غلط می‌سازد. همیشه تست را اجرا کن.

🧰 استراتژی‌های پیشرفتهٔ merge

ابزارها
git merge -X ours feat/x       # در تعارض، ما برنده
git merge -X theirs feat/x
git log --merge                # فقط کامیت‌های درگیر تعارض
git checkout --conflict=diff3 -- file

diff3 جد مشترک را هم نشان می‌دهد — برای تعارض سخت طلایی است. در VS Code: "merge-conflict.diff3": true (یا Merge Editor).

VS Code Merge Editor سه‌ستونه (Incoming / Current / Result) را از Command Palette با Merge Conflict: Open Merge Editor باز می‌کند.

سؤالات مصاحبه (با پاسخ)

Junior — fast-forward یعنی چه؟ حرکت اشاره‌گر بدون کامیت جدید، چون تاریخچه خطی بوده.

Mid — چرا squash در main تاریخچه را «دروغ» می‌کند؟ چون چند کامیت واقعی به یک کامیت تبدیل می‌شوند؛ bisect و blame جزئیات را از دست می‌دهند — ولی PR تمیز می‌ماند.

Senior — recursive در برابر ort؟ از Git ۲.۳۴ موتور پیش‌فرض ort است؛ سریع‌تر و پیش‌بینی‌پذیرتر از recursive قدیمی.

✅ چک‌لیست فهم

  • سه نوع ادغام را بلدی
  • تعارض را در VS Code حل کرده‌ای
  • merge --abort را حفظی بلدی
  • می‌دانی squash چه چیزی را پنهان می‌کند

Undo — restore، reset، revert و reflog

Undo در Git یک فرمان نیست — چهار کار مختلف است. قبل از اجرا باید بدانی فایل روی دیسک را برمی‌گردانی، پیش‌نویس را خالی می‌کنی، اشاره‌گر شاخه را حرکت می‌دهی، یا یک کامیت جدیدِ خنثی می‌سازی.

🎯 اهداف یادگیری

  • نقشهٔ Undo را از حفظ بکشی
  • restore را جایگزین checkout فایل کنی
  • سه حالت reset را از هم جدا کنی
  • با reflog کامیت «گمشده» را زنده کنی

شکل ۷ — قانون طلایی: تاریخچهٔ عمومی را فقط با revert لمس کن.

🧹 Working Tree و Index

بازگردانی فایل — مدرن
git restore src/auth.ts                 # Working ← Index
git restore --staged src/auth.ts        # Index ← HEAD
git restore --source=HEAD --staged --worktree src/auth.ts
# هر دو درخت فایل = HEAD  (معادل checkout -- file)
git restore --source=main~3 README.md   # نسخهٔ قدیمی را بیاور
🖥️ VS Code Git
  • Changes → آیکون ↩ Discard Changes = restore
  • Staged → - Unstage = restore --staged
  • منوی ... → Commit → Undo Last Commit = reset --soft
  • Timeline فایل را بعد از Discard هم گاهی نجات می‌دهد
  • Discard All خطرناک است
⌨️ Terminal

git restore file git restore --staged file git reset --soft HEAD~1 git reflog برای نجات

🧱 سه چهرهٔ reset

فرض: A--B--C (HEAD) و می‌خواهی به B برگردی.

فرمان HEAD Index Working استفاده
--soft B B محتوای C محتوای C کامیت را بشکن، تغییرات بماند staged
--mixed B (پیش‌فرض) B B محتوای C کامیت را بشکن، تغییرات unstaged
--hard B B B B همه‌چیز برود
مثال‌های امن
git reset --soft HEAD~1        # پیام/فایل‌ها را دوباره بچین
git reset HEAD~1               # همان، اما unstaged
# git reset --hard HEAD~1     # فقط اگر مطمئنی

در VS Code منوی ... در Source Control: Commit → Undo Last Commit معمولاً --soft.

هرگز reset --hard روی main مشترک

اگر push شده، تاریخچهٔ دیگران را تکه‌پاره می‌کنی. به‌جایش git revert.

↩️ revert — Undo عمومی

کامیت معکوس بساز
git revert HEAD                # آخرین را خنثی کن
git revert -m 1 <merge-sha>    # خنثی‌کردن merge (والد ۱ = شاخهٔ هدف)

Revert یک کامیت جدید می‌سازد که تغییرات را برعکس اعمال می‌کند. تاریخچه دروغ نمی‌گوید.

در GitHub: روی PR دگمهٔ Revert همین کار را تمیزتر انجام می‌دهد.

🛟 reflog — ماشین زمان اشاره‌گرها

هر حرکت HEAD در reflog ثبت می‌شود (معمولاً ۹۰ روز).

زنده کردن کامیت گمشده
git reflog
# e3a1... HEAD@{0}: reset: moving to HEAD~1
# 9f3a... HEAD@{1}: commit: feat(auth): ...

git switch -c rescue HEAD@{1}
# یا
git reset --hard 9f3a1c
چه چیزی را reflog نجات نمی‌دهد؟

فایلی که هرگز add/commit نشده و Discard شده. Git آن را ندیده. از Local History خود VS Code (Timeline) کمک بگیر.

در VS Code: Timeline گاهی نسخه‌های محلی ذخیره می‌کند حتی بدون Git — آخرین تور ایمنی برای Untracked.

سؤالات مصاحبه (با پاسخ)

Junior — تفاوت restore و reset؟ restore فایل‌محور است؛ reset اشاره‌گر شاخه را حرکت می‌دهد.

Mid — soft در برابر mixed؟ هر دو HEAD را حرکت می‌دهند؛ soft ایندکس را نگه می‌دارد.

Senior — revert یک merge چرا -m 1 می‌خواهد؟ چون merge دو والد دارد. باید بگویی «خط اصلی کدام است» تا diff معکوس معنا داشته باشد.

✅ چک‌لیست فهم

  • نقشهٔ Undo را بلدی
  • restore را به‌جای checkout فایل می‌زنی
  • --hard را برای کار عمومی ممنوع می‌دانی
  • یک‌بار با reflog نجات داده‌ای

نادیده‌گرفتن و فایل بزرگ — gitignore، attributes، LFS

اگر فایل رمز (مثل .env) یک‌بار git add شود، حتی بعد از حذف از پوشه در تاریخچه می‌ماند. این فصل می‌گوید چه چیزی را از اول وارد Git نکنی و فایل بزرگ را کجا بگذاری.

🎯 اهداف یادگیری

  • .gitignore مؤثر بنویسی و الگوی negating را بفهمی
  • فایل trackشده را بعداً ignore کنی
  • Git LFS را برای باینری بزرگ راه بیندازی
  • .gitattributes را برای eol و diff تنظیم کنی

🚫 gitignore — الگوها

.gitignore — نمونهٔ Node/Python
# وابستگی
node_modules/
.venv/
dist/
coverage/

# راز
.env
.env.*
!.env.example

# سیستم
.DS_Store
Thumbs.db

# ادیتور — اختیاری: بعضی تیم‌ها .vscode را commit می‌کنند
.idea/

اولویت: الگوی محلی فایل → پوشهٔ والد → ریشه → .git/info/exclude → core.excludesFile جهانی.

چرا هنوز دیده می‌شود؟
git check-ignore -v src/.env     # کدام قانون خورد؟
git rm --cached secrets.json     # از Index بردار، فایل روی دیسک بماند
فایل trackشده ignore نمی‌شود

اگر قبلاً add شده، باید git rm --cached کنی. فقط نوشتن در gitignore کافی نیست.

در VS Code فایل‌های ignoreشده در Explorer کم‌رنگ‌اند. Source Control آن‌ها را نشان نمی‌دهد مگر Show Ignored.

🌍 قالب جهانی

excludes سراسری
git config --global core.excludesFile ~/.gitignore_global
echo ".DS_Store" >> ~/.gitignore_global

📦 Git LFS — باینری را در تاریخچه خفه نکن

PDF، مدل سه‌بعدی، وزن شبکهٔ عصبی و فیلم با هر ویرایش کل blob را تکرار می‌کنند.

LFS
git lfs install
git lfs track "*.pdf"
git lfs track "*.psd"
git add .gitattributes
git add docs/book.pdf
git commit -m "chore: store pdf in LFS"
git lfs ls-files

روی GitHub فضای LFS جداگانه دارد (سهمیه). برای کتاب و بازی رایج است؛ برای کد منبع لازم نیست.

🧩 gitattributes

.gitattributes
* text=auto eol=lf
*.sh text eol=lf
*.bat text eol=crlf
*.png binary
*.pdf filter=lfs diff=lfs merge=lfs -text
package-lock.json merge=binary   # جلوگیری از merge درهم JSON قفل

eol=lf جنگ CRLF ویندوز/لینوکس را در تیم‌های چندسیستمی می‌کشد. در VS Code "files.eol": "\n".

قالب github

فایل .gitattributes با linguist-vendored می‌تواند آمار زبان مخزن را درست کند — مفید برای monorepo.

سؤالات مصاحبه (با پاسخ)

Junior — node_modules را commit کنیم؟ هرگز. قفل (package-lock) را بله، پوشه را خیر.

Mid — تفاوت exclude و gitignore؟ info/exclude شخصی و غیرقابل‌پوش است؛ gitignore تیمی است.

Senior — LFS pointer چیست؟ فایل متنی کوچک با OID و اندازه که به‌جای باینری در Git ذخیره می‌شود؛ محتوا روی LFS store است.

✅ چک‌لیست فهم

  • .env در تاریخچه نیست
  • check-ignore -v را بلدی
  • برای PDF از LFS استفاده می‌کنی
  • eol تیم یکسان است

Source Control از صفر — Ctrl+Shift+G

خانهٔ روزانهٔ Git در VS Code پنل Source Control است. میانبر ثابت این کتاب Ctrl+Shift+G است. اینجا هر کلیک را به ترتیب می‌نویسیم و برای هر تفاوت («چرا مال من این‌طور است؟») دلیل دقیق می‌آید.

🎯 اهداف یادگیری

  • پنل را با کلیک مشخص باز کنی و بدانی بعد از آن باید چه ببینی
  • اگر دکمه یا لیست تو با عکس کتاب یکی نبود، در همان لحظه علت را بدانی
  • یک فایل را از Save تا Commit، کلیک‌به‌کلیک، تمام کنی
  • Stage، Unstage، Discard و Stage Selected Ranges را بدون حدس بزنی

🧭 قبل از اولین کلیک — عکس کتاب مال یک حالت است

عکس‌های این فصل از یک VS Code واقعی‌اند: ویندوز، زبان انگلیسی، تم تیره، مخزنی که Working Tree تمیز است و origin پانزده کامیت جلوتر. صفحهٔ تو باید دکمه‌های همان‌جا را داشته باشد، نه لزوماً همان عدد ۱۵ یا همان نام فایل.

چیزی که در عکس می‌بینی مال تو ممکن است چرا؟
برچسب انگلیسی Source Control، Commit، Sync Changes فارسی: «کنترل منبع»، «ثبت»، «همگام‌سازی تغییرات» زبان نمایش VS Code. موقعیت دکمه یکی است؛ فقط نوشته عوض می‌شود.
تم تیرهٔ سرمه‌ای تم روشن یا تم دیگر رنگ عوض می‌شود؛ نام فرمان‌ها عوض نمی‌شود.
Sync Changes 15↓ Commit یا Publish Branch یا هیچ دکمهٔ آبی بستگی دارد تغییرات محلی داری یا نه، و آیا origin هست یا نه — پایین، سه حالت.
حرف M کنار src/auth.ts فایل و حرف دیگر، یا لیست خالی مثال کتاب است. تو فایل خودت را می‌بینی.
Graph پایین پنل Graph نیست نسخهٔ قدیمی VS Code، یا بخش جمع شده؛ فلش > را باز کن.
میانبر Ctrl+Shift+G در مک گاهی باید Cmd نباشد؛ همین Ctrl است در VS Code روی مک هم پیش‌فرض Ctrl+Shift+G است نه Cmd.
زبان عکس‌ها انگلیسی است عمداً

در شکل‌ها متن فارسی نمی‌گذاریم (برعکس می‌شود). اگر VS Code تو فارسی است، همان دکمه را از روی جایگاه پیدا کن نه از روی املای کتاب.

⌨️ باز کردن پنل — سه کلیک معادل، یکی کافی است

یکی از این سه را بزن؛ هر سه باید همان ستون چپ را باز کنند:

  1. صفحه کلید: Ctrl+Shift+G (ویندوز، لینوکس، مک)
  2. ماوس: در نوار باریک چپ (Activity Bar) روی آیکون شاخه/Git کلیک کن — در عکس کتاب شمارهٔ ۱
  3. اگر هیچ‌کدام کار نکرد: Ctrl+Shift+P → تایپ کن View: Show Source Control → Enter

بعد از باز شدن باید ببینی: ستون سمت چپ با عنوان Source Control. ادیتور سمت راست سر جایش می‌ماند.

اگر مال تو این‌طور نیست:

چه دیدی علت چه کار کن
هیچ پنلی باز نشد فوکوس روی ترمینال است و میانبر قورت داده شد یک‌بار روی ادیتور کلیک کن، دوباره Ctrl+Shift+G
پنل Explorer باز شد نه Git آیکون اشتباه (دو سند بالا) آیکون سوم/چهارم Activity Bar؛ یا همان Palette
ستون آمد ولی نوشته Git not found / Git not installed VS Code فایل git.exe را پیدا نکرده Palette → Git: Show Git Output. Settings → git.path را به مسیر نصب Git بده. از نو VS Code را باز کن
ستون آمد، کاملاً خالی، بدون Message پوشه باز نیست File → Open Folder روی پوشهٔ پروژه

🧭 آناتومی — بعد از باز شدن، این چهار نقطه را لمس کن

شکل ۹ — برش نزدیک. شماره‌ها را با فهرست زیر تطبیق بده. دکمهٔ آبی اینجا Sync است نه Commit؛ برای تو ممکن است برعکس باشد.

  1. کلیک روی آیکون Git در Activity Bar. اگر روی آیکون عدد بود یعنی فایل تغییرکرده داری. اگر عدد نبود، یا Working Tree تمیز است یا نشان روی آیکون دیگری است (در عکس کامل کتاب، نشان آبی روی Extensions است نه Git — این باگ نیست).
  2. عنوان Source Control و سه‌نقطهٔ ··· بالا-راست. یک کلیک روی ··· منوی Fetch / Pull / Push / Stash را باز می‌کند (فصل ۱۱).
  3. یک کلیک داخل جعبهٔ Message — مکان‌نما باید چشمک بزند. این‌جا متن کامیت را می‌نویسی. Ctrl+Enter فقط وقتی کار می‌کند که فوکوس همین جعبه باشد.
  4. دکمهٔ بزرگ زیر جعبه — برچسبش ثابت نیست. VS Code بر اساس وضعیت مخزن یکی از این‌ها را می‌نویسد: Initialize Repository، Publish Branch، Commit، Sync Changes، یا Commit (merge).

پایین همان ستون، بدون عوض کردن پنل:

  • Graph — یک کلیک روی > یا روی کلمهٔ Graph. اگر نبود، VS Code را به‌روز کن یا Palette → Git: View History.
  • نوار وضعیت پایین-چپ پنجره (نه داخل ستون): نام شاخه. یک کلیک روی نام شاخه = فهرست عوض کردن شاخه.

شکل ۹ب — یک کلیک روی main. عدد ↓ و ↑ مال این مخزن است؛ مال تو ۰ و ۰ هم طبیعی است.

اگر نوار وضعیت شاخه نشان نمی‌دهد: یا پوشه Git ندارد، یا Git پیدا نشده. اول همان جدول «اگر مال تو این‌طور نیست» را بالا ببین.

😶 دکمهٔ بزرگ زیر Message — از روی برچسب بفهم کجایی

VS Code یک دکمهٔ اصلی دارد. برچسب را بخوان؛ حدس نزن.

حالت ۱ — نوشته Initialize Repository / Publish to GitHub

یعنی پوشه‌ای که Open Folder کرده‌ای فایل .git ندارد.

شکل ۹پ — فقط وقتی `.git` نیست این دو دکمه را می‌بینی.

کلیک‌ها:

  1. File → Open Folder — پوشهٔ خود پروژه را انتخاب کن، نه درایو و نه پوشهٔ والد.
  2. Ctrl+Shift+G.
  3. یک کلیک روی Initialize Repository. معادل git init. بعد از کلیک باید جعبهٔ Message ظاهر شود و اگر فایلی باشد، لیست Changes پر شود.
  4. همان لحظه فایل .gitignore بساز (Ctrl+N، ذخیره با همین نام) تا node_modules در Changes نیاید.
  5. Publish to GitHub را فقط اگر می‌خواهی ریپو روی GitHub ساخته شود بزن. اگر بزنی و وارد حساب نباشی، پنجرهٔ ورود مرورگر باز می‌شود — این خطا نیست.

اگر بعد از Initialize هنوز همان دو دکمه را می‌بینی: پوشهٔ اشتباه باز است. در Explorer باید .git را (گاهی مخفی) ببینی. File → Open Folder را تکرار کن.

اگر Publish خاکستری است یا خطا می‌دهد: Accounts پایین Activity Bar → Sign in to GitHub. بدون ورود، Publish کار نمی‌کند؛ Initialize کار می‌کند.

حالت ۲ — نوشته Sync Changes (شاید با عدد ↓ یا ↑)

یعنی مخزن هست، فایل ذخیره‌شدهٔ تغییرکرده برای کامیت نداری، ولی با origin هم‌تراز نیستی.

  • ۱۵↓ = روی سرور ۱۵ کامیت هست که تو نداری → Sync تقریباً pull است.
  • ↑۳ = تو ۳ کامیت داری که سرور ندارد → Sync تقریباً push است.
  • هر دو = واگرایی؛ Sync ممکن است merge بسازد.

لیست Changes خالی در این حالت موفقیت است (nothing to commit, working tree clean)، نه اینکه Git خراب باشد.

اگر Sync را زدی و از تو تأیید خواست: تنظیم git.confirmSync روشن است — Yes بگو یا در Settings خاموشش کن.

اگر Sync خطا داد (rejected / diverged): فصل ۱۱ — اول Fetch، بعد Pull یا Pull (Rebase). Force نزن.

حالت ۳ — نوشته Commit (یا Commit با فلش ▾)

یعنی حداقل یک فایل در Changes یا Staged هست.

اگر تو Commit می‌بینی و کتاب Sync: تو فایل ذخیره‌نشده یا تغییرکرده داری؛ کتاب در آن عکس Working Tree تمیز نشان می‌دهد. هر دو درست‌اند.

✍️ مسیر کامل کامیت — کلیک به کلیک

هدف: یک فایل را عوض کنی و در تاریخچه ثبت شود.

شکل ۱۰ — بعد از مرحلهٔ ۴ باید چیزی شبیه این ببینی: پیام، فایل‌ها با M/U، diff سبز/قرمز.

  1. فایل را در ادیتور عوض کن و Ctrl+S بزن.
    باید ببینی: روی آیکون Git عدد می‌آید؛ فایل در Changes ظاهر می‌شود.
    اگر نیامد: Save نشده، یا فایل داخل .gitignore است، یا پوشهٔ دیگری Open است.

  2. Ctrl+Shift+G.
    باید ببینی: نام فایل + حرف M یا U.

  3. یک کلیک روی نام فایل در Changes.
    باید ببینی: سمت راست، diff. خط قرمز = حذف، سبز = اضافه.
    اگر سمت راست همان Welcome VS Code ماند: روی نام فایل کلیک نشده؛ روی فضای خالی ستون کلیک کرده‌ای.

  4. یک کلیک روی + سمت راست همان فایل (وقتی نشانگر روی ردیف است ظاهر می‌شود). معادل git add.
    باید ببینی: فایل از Changes به Staged Changes می‌پرد.
    اگر + نبود: نشانگر را روی ردیف فایل ببر. در بعضی تم‌ها + فقط hover است. یا Palette → Git: Stage Changes.

  5. یک کلیک داخل جعبهٔ Message و بنویس مثلاً feat(auth): add JWT refresh flow.
    اگر جعبه غیرفعال است: هنوز Staged نداری و Smart Commit خاموش است — مرحلهٔ ۴ را بزن. یا فوکوس روی ادیتور است.

  6. Ctrl+Enter (مک: Cmd+Enter) یا یک کلیک روی دکمهٔ Commit.
    باید ببینی: لیست خالی می‌شود، دکمه ممکن است به Sync/Publish عوض شود، نوار وضعیت ↑1 بگیرد اگر remote داری.

اگر کلیک Commit همهٔ فایل‌ها را برد نه فقط یکی: git.enableSmartCommit روشن است. Settings → این گزینه را Off کن. از این به بعد بدون Stage، دکمه Commit کار نمی‌کند یا هشدار می‌دهد.

اگر خطا Signing failed / secret key: فصل ۲ — امضا روشن است ولی کلید SSH signing روی این ماشین نیست. موقتاً git.enableCommitSigning را Off کن یا کلید را بساز.

اگر خطا Please tell me who you are: user.name و user.email ست نشده — فصل ۲.

📦 Staged در برابر Changes — دو کلیک معکوس

شکل ۱۰ب — بالا می‌رود داخل کامیت؛ پایین هنوز نمی‌رود. اگر فقط یک لیست می‌بینی، یا چیزی Stage نکرده‌ای یا Untracked جداست.

می‌خواهی کلیک دقیق باید ببینی
فایل برود برای کامیت + روی ردیف در Changes ردیف می‌پرد به عنوان Staged Changes
پشیمان از Stage - روی ردیف در Staged برمی‌گردد به Changes؛ فایل روی دیسک همان است
همه را Stage + روی نوار عنوان Changes (نه روی فایل) همه می‌روند بالا
تغییرات فایل روی دیسک دور ریخته شود راست‌کلیک روی ردیف Changes → Discard Changes → تأیید فایل از لیست می‌رود؛ محتوای ادیتور به نسخهٔ قبلی برمی‌گردد

اگر Staged Changes را به‌عنوان عنوان جدا نمی‌بینی: هنوز + نزدی. با Smart Commit روشن، ممکن است بدون این عنوان هم Commit همه را بگیرد — برای همین خاموشش کردیم.

اگر Discard را زدی و فایل برگشت: Untracked (U) را Discard کردن یعنی حذف فایل از دیسک. VS Code معمولاً «Are you sure?» می‌پرسد. اگر پرسید و Yes گفتی، از Timeline برگردان (پایین فصل).

اگر Untrackedها ته یک لیست قاطی‌اند نه گروه جدا: Settings → git.untrackedChanges را بگذار separate.

🔬 hunk — سه کلیک آبی روی خود diff

hunk = چند خط سبز/قرمز پشت‌سرهم. معادل git add -p.

شکل ۱۰پ — این سه لینک آبی فقط وقتی فایل را از Changes باز کرده باشی بالای hunk ظاهر می‌شوند.

  1. در Changes یک کلیک روی فایل.
  2. در diff، خطوطی که می‌خواهی را با ماوس رنگ کن (یا هیچی انتخاب نکن اگر کل hunk را می‌خواهی).
  3. یک کلیک روی یکی از سه لینک آبی بالای hunk:
    • Stage Change = کل این hunk
    • Stage Selected Ranges = فقط خطوط انتخاب‌شده
    • Discard Change = همین hunk از روی دیسک برگردد

باید ببینی: اگر فقط بخشی Stage شد، فایل هم در Staged می‌ماند هم در Changes (حرف گاهی M دو جا). این درست است.

اگر لینک آبی نبود:

  • diff را از Timeline باز کرده‌ای نه از Changes — ببند، از Source Control روی فایل کلیک کن.
  • روی نمای پیش‌نمایش Markdown هستی نه متن — روی تب فایل خام کلیک کن.
  • تنظیم diffEditor.renderSideBySide فرق ندارد؛ لینک‌ها باید باشند. VS Code را به‌روز کن.

▾ فلش کنار Commit — یک کلیک، پنج فرمان

یک کلیک روی فلش ▾ سمت راست دکمهٔ Commit (نه خود Commit).

شکل ۱۰ت — اگر فلش را نمی‌بینی، دکمه هنوز Commit نیست (Sync/Publish است) یا عرض ستون خیلی کم است؛ ستون را بکش عریض‌تر کن.

کلیک روی چه می‌شود اگر مال تو خاکستری / نیست
Commit فقط ثبت محلی باید Staged یا Smart Commit داشته باشی
Commit & Push ثبت + ارسال به origin origin نباشد → اول Publish Branch
Commit & Sync ثبت + pull/push tracking نداشته باشی، Push جدا بزن
Undo Last Commit آخرین کامیت باز می‌شود، فایل‌ها Staged می‌مانند کامیت نداری
Amend آخرین کامیت را با Stage فعلی و پیام جدید عوض می‌کند بعد از push نزن
Amend بعد از push

هش عوض می‌شود. اگر همکار آن کامیت را گرفته، تاریخچه دوپاره می‌شود.

Ctrl+Enter فقط داخل جعبهٔ Message کامیت می‌زند. اگر فوکوس روی ادیتور باشد، ممکن است کار دیگری بکند یا هیچ.

یک کلیک داخل Message، بعد Ctrl+Enter. اگر عادت شد: بعد از Stage، کلیک Message، میانبر.

🧵 Timeline — این یکی داخل Source Control نیست

کلیک‌ها: آیکون Explorer بالا-چپ Activity Bar (دو سند) → فایل را در درخت انتخاب کن → پایین همان ستون تب Timeline را باز کن (اگر جمع است، عنوان Timeline را کلیک کن).

شکل ۱۰ث — اگر Timeline خالی است، فایل را انتخاب نکرده‌ای یا Git در این پوشه نیست.

یک کلیک روی یک ردیف Timeline آن نسخه را مقایسه می‌کند. Local History برای Discard فایل Untracked است.

🧪 تمرین — هر کدام را تا «باید ببینی» پیش برو

تمرین ۱. پوشهٔ خالی Open Folder → باید Initialize ببینی → کلیک Initialize → README.md بساز و Save → باید U در Changes → + → Message docs: add readme → Ctrl+Enter → باید لیست خالی شود.

تمرین ۲. سه فایل را Save کن → فقط روی یکی + → Commit → باید دو فایل در Changes مانده باشد. اگر هر سه رفتند، Smart Commit را Off کن و تمرین را تکرار کن.

تمرین ۳. یک فایل را چند خط عوض کن → از Changes باز کن → فقط بعضی خط‌ها را Stage Selected Ranges بزن → باید فایل هم بالا هم پایین باشد.

تمرین ۴. Discard یک M → از Timeline برگردان.

Source Control فوق‌پیشرفته — Graph تا PR

Graph، شاخه، Sync، تعارض، rebase و PR همه از همان Ctrl+Shift+G می‌آیند. مثل فصل ۱۰: هر کار یعنی چند کلیک مشخص، چه باید ببینی، و اگر مال تو فرق داشت یعنی چه.

🎯 اهداف یادگیری

  • Graph را با کلیک باز کنی و از راست‌کلیک روی کامیت نترسی
  • Fetch / Pull / Push / Sync را از روی منو جدا بزنی و بدانی چرا دکمهٔ تو با کتاب یکی نیست
  • تعارض و rebase را تا آخرین کلیک (Continue یا Abort) تمام کنی
  • اگر Graph، Incoming یا افزونهٔ PR نبود، علت را بدانی

📈 Graph — باز کردن و راست‌کلیک

کلیک‌ها برای باز شدن:

  1. Ctrl+Shift+G.
  2. ته ستون Source Control روی Graph یک کلیک (اگر > دیدی، همان را باز کن).
  3. اگر Graph نبود: Ctrl+Shift+P → Git: View History → Enter.

شکل ۱۱ — برش نزدیک. رنگ‌ها و هش‌ها مثال‌اند؛ تو کامیت‌های مخزن خودت را می‌بینی.

باید ببینی: خط‌های رنگی، هش کوتاه، پیام کامیت، گاهی برچسب main / HEAD.

اگر مال تو این‌طور نیست:

چه دیدی علت چه کار کن
اصلاً Graph در ستون نیست VS Code قدیمی‌تر از حدود ۱.۹۷ VS Code را به‌روز کن؛ یا افزونهٔ Git Graph / GitLens
Graph باز شد ولی یک نقطه است مخزن فقط یک کامیت دارد طبیعی است
Incoming خالی است با اینکه همکار push کرده Fetch نشده منوی ··· → Fetch (پایین)
راست‌کلیک منوی کوتاه دارد روی پیام کلیک کرده‌ای نه روی گره، یا افزونه منو را عوض کرده روی دایرهٔ کامیت راست‌کلیک کن

راست‌کلیک روی یک دایره / ردیف کامیت، بعد یک کلیک روی فرمان:

فرمان بعد از کلیک چه می‌شود اگر ترسیدی

Create Branch جعبهٔ نام می‌پرسد Enter بزن؛ معادل git switch -c

🌿 عوض کردن و ساختن شاخه — از نوار وضعیت

کلیک ۱: پایین-چپ پنجره، روی نام شاخه (مثلاً main).
باید ببینی: فهرست بالا وسط ادیتور (Quick Pick).

شکل ۱۱ب — اگر این فهرست نیامد، روی نام شاخه کلیک نشده یا Git پیدا نشده.

کلیک ۲ — تعویض: روی نام شاخهٔ دیگر.
باید ببینی: نوار وضعیت همان نام را می‌گیرد؛ فایل‌های ادیتور عوض می‌شوند.

اگر خطا Your local changes would be overwritten: تغییرات ذخیره‌شده داری. اول Commit یا Stash (منوی ··· → Stash)، بعد دوباره نام شاخه را کلیک کن.

کلیک ۲ — ساختن: روی + Create new branch from... → یک کلیک روی پایه‌ای که می‌خواهی (main) → نام را تایپ کن مثلاً feat/auth → Enter.

شکل ۱۱پ — همین کار از Palette با Git: Create Branch from... هم می‌شود.

کلیک Publish Branch: در همان فهرست یا روی دکمهٔ ابری نوار وضعیت. اولین push است (-u).

اگر Publish می‌خواهد وارد GitHub شوی: Accounts پایین Activity Bar → Sign in. بدون origin، دکمهٔ اصلی پنل به‌جای Sync می‌ماند Publish.

اگر شاخهٔ جدید در فهرست نیست: هنوز Enter ساختن را نزدی، یا refresh لازم است: ··· → Refresh.

📡 منوی ··· — هر فرمان یک کلیک، Sync آخرین انتخاب

کلیک: بالا-راست ستون Source Control روی ··· (شمارهٔ ۲ آناتومی فصل ۱۰).

شکل ۱۱ت — ترتیب پیشنهادی: اول Fetch، نگاه به ↓↑، بعد Pull یا Push. Sync میان‌بر هر دوست.

کلیک روی باید بعدش ببینی مال تو فرق دارد اگر
Fetch عدد ↓ در نوار وضعیت زیاد شود، Graph Incoming پر شود؛ فایل‌ها عوض نمی‌شوند اینترنت/SSH نیست؛ یا origin نداری
Pull فایل‌ها ممکن است عوض شوند؛ ↓ صفر شود تعارض → بخش بعد. اگر rebaseWhenSync روشن باشد ممکن است rebase شروع شود
Pull (Rebase) اگر تعارض باشد نوار زرد Rebase روی main مشترک نزن
Push ↑ صفر شود rejected = کسی push کرده؛ Fetch کن نه Force
Sync ترکیب pull/push اگر confirmSync روشن باشد یک Yes اضافه می‌پرسد — این «خراب بودن» نیست
Stash (Include Untracked) Changes خالی می‌شود بدون Include، فایل‌های U می‌مانند و switch شکست می‌خورد
Undo Last Commit فایل‌ها برمی‌گردند به Staged اگر push کرده باشی، بعداً Push rejected می‌شود
Discard All Changes همهٔ فایل‌های M از لیست می‌روند پنجرهٔ Are you sure؟ — Yes یعنی از دست رفتن کار ذخیره‌نشده

نوار وضعیت ↑1 ↓2 یعنی ۱ کامیت برای push و ۲ برای pull. عدد تو با کتاب یکی نمی‌شود و نباید بشود.

💥 تعارض — از حرف C تا Commit (merge)

تعارض فقط بعد از Merge / Pull / Cherry-pick / Rebase می‌آید. اگر هیچ‌کدام را نزدی و C دیدی، احتمالاً merge ناتمام قبلی مانده: Palette → Git: Abort Merge.

باید ببینی: در Source Control عنوان Merge Changes و فایل با حرف C. دکمهٔ اصلی ممکن است بشود Accept Merge / Commit (merge).

شکل ۱۱ث — نوار آبی چهار فرمان فقط روی فایل C بازشده از Source Control است.

کلیک‌ها:

  1. یک کلیک روی فایل C.
  2. بالای بلوک قرمز/سبز، یک کلیک روی یکی از:
    • Accept Current Change = نسخهٔ شاخه‌ای که روی آن بودی (HEAD / Ours)
    • Accept Incoming Change = نسخه‌ای که داشتی وارد می‌کردی (Theirs)
    • Accept Both Changes = هر دو پشت‌سرهم؛ بعد خودت ویرایش کن
    • Compare Changes = دو ستون
  3. Ctrl+S.
  4. یک کلیک روی + همان فایل (Stage). حرف C باید برود.
  5. یک کلیک روی Commit (merge) یا Ctrl+Enter با پیام پیش‌فرض merge.

اگر نوار Accept نبود: Palette → Merge Conflict: Open Merge Editor — سه ستون Incoming / Current / Result. Result را درست کن → Accept Merge.

اگر هنوز C می‌ماند: Save و Stage را نزدی. یا چند تعارض در همان فایل است — همه را Accept کن.

پشیمانی قبل از مرحلهٔ ۵: Palette → Git: Abort Merge. بعد از Commit دیگر abort نیست؛ باید revert.

🔁 Rebase ناتمام — نوار زرد را تا انتها دنبال کن

بعد از Pull (Rebase) یا Git: Rebase Branch... اگر تعارض باشد:

باید ببینی: در پنل «Rebase in progress»، در بالا ادیتور نوار زرد، دکمه‌های Continue / Abort.

شکل ۱۱ج — تا این نوار هست، دکمهٔ معمولی Commit را نزن. VS Code عمداً کامیت عادی را قفل یا گمراه‌کننده می‌کند.

کلیک‌ها:

  1. فایل C را مثل تعارض حل کن → Save → + (Stage).
  2. یک کلیک Continue (= git rebase --continue).
  3. اگر تعارض بعدی آمد، ۱ و ۲ را تکرار کن تا نوار زرد برود.

اگر Continue خاکستری است: هنوز همهٔ فایل‌های C را Stage نکرده‌ای، یا Message rebase خالی است — جعبهٔ Message را خالی نگذار.

پشیمانی: یک کلیک Abort. همه چیز برمی‌گردد به قبل از rebase.

اگر وسط rebase VS Code را بستی و باز کردی: نوار زرد باید برگردد. اگر نماند، Palette → Git: Continue Rebase یا Abort Rebase.

📚 چند مخزن در یک پنجره

کلیک‌ها: File → Add Folder to Workspace → پوشهٔ دوم که خودش .git دارد.

باید ببینی: در Source Control چند عنوان Repository. یک کلیک روی عنوان، آن مخزن را جمع/باز می‌کند.

شکل ۱۱چ — اگر فقط یکی می‌بینی، پوشهٔ دوم Git ندارد یا هنوز Add Folder نکرده‌ای.

اگر Commit روی مخزن غلط نشست: عنوان همان Repository را باز کن، بعد Message را بزن. VS Code روی مخزن «فعال» کامیت می‌کند.

worktree: در ترمینال git worktree add -b hotfix/500 ../hotfix main بعد File → Add Folder روی ../hotfix. یک شاخه در دو worktree هم‌زمان باز نمی‌شود — پیام خطا را با Stash یا عوض کردن شاخه حل کن.

📬 Pull Request — افزونه، نه خود Git توکار

Source Control توکار PR نمی‌سازد. باید افزونهٔ GitHub Pull Requests نصب باشد.

کلیک نصب: Activity Bar آیکون Extensions (یا Ctrl+Shift+X) → جست‌وجو GitHub Pull Requests → Install → Accounts پایین Activity Bar → Sign in to GitHub → مرورگر Allow.

اگر آیکون GitHub در Activity Bar نیامد: افزونه نصب نشده یا غیرفعال است. View → Appearance → Activity Bar را چک کن.

شکل ۱۲ — این نما مال افزونه است نه ستون Git. اگر ندیدی، Sign in نشده.

ساخت PR از شاخهٔ فعلی:

  1. اول Push / Publish Branch از Source Control (وگرنه GitHub شاخه را ندارد).
  2. Ctrl+Shift+P → GitHub Pull Requests: Create Pull Request.
  3. عنوان و پایه (main) را تأیید کن → Create.

اگر Create خطا می‌دهد no upstream: Publish Branch را جا انداختی.

ریویو: آیکون GitHub → یک کلیک روی PR → Checkout → در Files Changed روی خط کلیک → کامنت → Approve.

اگر Checkout PR فایل‌های تو را overwrite می‌کند: اول Commit یا Stash از ستون Source Control.

دیدن تغییر — diff، log، blame و bisect

برای فهمیدن «چه عوض شد» فایل کامل را نخوان — تفاوت دو نسخه را بخوان. این فصل سه نوع diff، فیلتر log، و پیدا کردن کامیت خراب با bisect را جدا می‌کند.

🎯 اهداف یادگیری

  • diff سه سطحی (unstaged / staged / بین کامیت‌ها) را جدا کنی
  • log را فیلتر کنی تا در ده هزار کامیت گم نشوی
  • با bisect باگ را در log₂(n) قدم پیدا کنی

📐 سه diff

سه نگاه
git diff                  # Working vs Index
git diff --staged         # Index vs HEAD
git diff main...HEAD      # سه نقطه: از جد مشترک
git diff main..HEAD       # دو نقطه: تفاوت نوک‌ها
سه‌نقطه در برابر دونقطه

A...B یعنی «تغییرات B از وقتی از A جدا شد» — دقیقاً همان چیزی که PR نشان می‌دهد. A..B نوک A را با نوک B مقایسه می‌کند و ممکن است تغییرات نامرتبط A را هم بیاورد.

در VS Code کلیک روی فایل Changes = git diff. کلیک روی Staged = git diff --staged. Open Changes با Alt گاهی side-by-side را عوض می‌کند.

diff بهتر
{
  "diffEditor.renderSideBySide": true,
  "diffEditor.ignoreTrimWhitespace": false,
  "diffEditor.hideUnchangedRegions.enabled": true
}

hideUnchangedRegions در فایل‌های بزرگ ۲۰۲۶ نجات‌دهنده است.

📜 log حرفه‌ای

جست‌وجوی تاریخچه
git log --grep="refresh" -i
git log -S "rotateToken" -p          # pickaxe: کی این رشته آمد/رفت؟
git log -G "function rotate" -p      # regex روی diff
git log --since="2026-01-01" --until="2026-03-01" -- src/auth.ts
git log --no-merges --first-parent   # خط اصلی محصول

--first-parent روی main پر از merge، داستان محصول را می‌خواند نه داستان شاخه‌ها را.

🎯 bisect — کارآگاه باینری

پیدا کردن کامیت خراب
git bisect start
git bisect bad                # HEAD خراب است
git bisect good v1.2.0        # این تگ سالم بود
# Git وسط را checkout می‌کند — تست کن
git bisect good               # یا bad
git bisect reset

اسکریپت‌پذیر:

bisect خودکار
git bisect start HEAD v1.2.0
git bisect run npm test

در VS Code می‌توانی هر گام را از Graph با Checkout انجام دهی؛ اما bisect run در ترمینال سریع‌تر است.

-w و ignore-revs

برای blame تمیز: فایل .git-blame-ignore-revs با هش کامیت‌های format-only، بعد:

git config blame.ignoreRevsFile .git-blame-ignore-revs

سؤالات مصاحبه (با پاسخ)

Junior — git diff بدون آرگومان چه می‌کند؟ Working در برابر Index.

Mid — pickaxe چیست؟ -S کامیت‌هایی را می‌آورد که تعداد رخداد یک رشته را عوض کرده‌اند.

Senior — چرا first-parent برای main مهم است؟ چون هر merge یک دنیای موازی است؛ برای رگرسیون محصول معمولاً فقط خط اصلی اهمیت دارد.

✅ چک‌لیست فهم

  • A...B را از A..B جدا می‌کنی
  • -S را برای یافتن تولد یک تابع بلدی
  • یک bisect موفق انجام داده‌ای

کار موازی — stash، worktree و sparse-checkout

اگر وسط یک فیچر ناقص باگ تولید آمد، دو راه تمیز داری: تغییرات را موقتاً کنار بگذار (stash) یا همان مخزن را در پوشهٔ دوم روی شاخهٔ دیگر باز کن (worktree). کامیت الکی روی فیچر نزن.

🎯 اهداف یادگیری

  • stash را با پیام نام‌گذاری کنی و درست برگردانی
  • worktree را برای کار همزمان روی دو شاخه راه بیندازی
  • sparse-checkout را در monorepo بفهمی

📥 stash — قفسهٔ موقت

stash تمیز
git stash push -u -m "wip: jwt tests"
git stash list
git stash show -p stash@{0}
git stash pop                  # اعمال + حذف
git stash apply stash@{1}      # اعمال، نگه داشتن
git stash drop stash@{1}
git stash branch rescue stash@{0}

-u فایل Untracked را هم می‌گیرد. بدون آن notes.txt جدید جا می‌ماند و switch ممکن است شکست بخورد.

🖥️ VS Code Git

Source Control → ... → Stash

  • Stash (Include Untracked)
  • Stash All
  • Pop Latest Stash / Apply Latest Stash لیست stashها در همان منو دیده می‌شود.
⌨️ Terminal

git stash push -u -m "wip" git stash pop git stash apply stash@{1}

شکل ۱۳ — منوی ··· در Source Control: Fetch، Pull (Rebase)، Stash، Undo Last Commit و Sync در نوار وضعیت.

stash pop تعارض

اگر تعارض آمد، stash حذف نمی‌شود (pop شکست می‌خورد). حل کن، بعد drop. apply در این مواقع شفاف‌تر است.

🌲 worktree — چند checkout واقعی

worktree یعنی یک پوشهٔ دوم از همان پروژه، روی شاخه‌ای دیگر. فایل‌ها جدایند، اما تاریخچه (پوشهٔ .git) مشترک است — پس کامیت در پوشهٔ دوم در همان مخزن ثبت می‌شود.

هات‌فیکس کنار فیچر
# از مخزن اصلی
git worktree add ../app-hotfix -b hotfix/500 main
code -n ../app-hotfix
# بعد از اتمام
git worktree remove ../app-hotfix
git worktree list

قواعد:

  • یک شاخه در دو worktree همزمان checkout نمی‌شود
  • برای PR موازی و عامل‌های AI (فصل ۳۲) ایده‌آل است
  • remove قبل از پاک کردن پوشه

VS Code هر worktree را به‌صورت پوشهٔ جدا باز می‌کند — Source Control مستقل، تاریخچه مشترک.

📦 sparse-checkout و partial clone

در monorepo که ۱۰ گیگ است، کل درخت را لازم نداری.

فقط پوشهٔ خودت
git clone --filter=blob:none --sparse git@github.com:org/mono.git
cd mono
git sparse-checkout set apps/web packages/ui

--filter=blob:none (partial clone) blobها را تنبلانه می‌گیرد. GitHub این را پشتیبانی می‌کند. Scalar (ابزار مایکروسافت) همین ایده را برای ویندوز بزرگ خودکار می‌کند — فصل ۳۱.

سؤالات مصاحبه (با پاسخ)

Junior — stash کجا ذخیره می‌شود؟ refهای refs/stash و کامیت‌های merge-مانند در objects.

Mid — کی worktree، کی stash؟ stash برای دقیقه؛ worktree برای ساعت و روز و PR موازی.

Senior — چرا شاخه در دو worktree ممنوع است؟ چون هر دو HEAD و Index می‌خواهند همان ref را حرکت دهند — مسابقه.

✅ چک‌لیست فهم

  • stash با پیام می‌سازی نه stash@{7} بی‌نام
  • یک worktree واقعی باز کرده‌ای
  • فرق partial clone و sparse را بلدی

Remote — fetch، pull، push و tracking

Remote فقط یک نام برای آدرس مخزن روی سرور است (معمولاً origin). Tracking یعنی شاخهٔ محلی تو به کدام شاخهٔ سرور وصل است — از روی آن Git می‌گوید چند کامیت جلوتر یا عقب‌تری.

🎯 اهداف یادگیری

  • origin را به‌عنوان نام مستعار URL توضیح دهی
  • fetch را از pull جدا کنی
  • -u و شاخهٔ بالادست را تنظیم کنی
  • force-with-lease را به‌جای force خام استفاده کنی

🌐 Remote چیست؟

دیدن و ساختن
git remote -v
# origin  git@github.com:rezaian-dev/git-lab.git (fetch)
# origin  git@github.com:rezaian-dev/git-lab.git (push)

git remote add origin git@github.com:rezaian-dev/git-lab.git
git remote set-url origin git@github.com:rezaian-dev/git-lab.git

در VS Code: Publish Branch اگر origin نباشد، ویزارد GitHub را باز می‌کند.

📡 fetch ≠ pull

فرمان چه می‌کند
git fetch اشیای جدید را می‌آورد؛ شاخهٔ محلی را حرکت نمی‌دهد
git fetch --prune refهای حذف‌شده روی سرور را محلی پاک می‌کند
git pull fetch + merge (یا rebase اگر تنظیم شده)
git pull --ff-only فقط اگر fast-forward ممکن باشد — امن‌ترین pull
عادت پیشنهادی
git fetch origin
git log --oneline HEAD..origin/main    # چه چیزی می‌آید؟
git merge --ff-only origin/main
🖥️ VS Code Git
  • Publish Branch اولین push و ساخت origin (با ورود GitHub)
  • آیکون ↻ Sync = pull سپس push
  • منوی ... جداگانه: Fetch / Pull / Push / Pull (Rebase)
  • نوار وضعیت: ↑1 ↓2 یعنی ahead/behind
  • git.autofetch: true در پس‌زمینه fetch می‌کند
⌨️ Terminal

git fetch origin git pull --ff-only git push -u origin HEAD

شکل ۱۴ب — نوار وضعیت: ↑ ahead و ↓ behind. دکمهٔ Sync همان pull سپس push است.

📌 tracking

بالادست
git switch -c feat/auth
git push -u origin HEAD          # -u = --set-upstream
git status -sb
# ## feat/auth...origin/feat/auth [ahead 1, behind 2]
  • ahead = کامیت محلی که remote ندارد
  • behind = کامیت remote که محلی نداری
  • هر دو = واگرایی → باید merge یا rebase کنی قبل از push

🚀 push امن

هرگز --force خام روی شاخهٔ مشترک
git push --force-with-lease
# اگر کس دیگری push کرده باشد، رد می‌شود

--force کورکورانه تاریخچهٔ سرور را عوض می‌کند. --force-with-lease فقط اگر remote همان چیزی باشد که تو آخرین‌بار دیدی.

در VS Code هنگام Push اگر rejected شدی، Force Push را نزن مگر روی شاخهٔ شخصی.

--force روی main

در Rulesets باید ممنوع باشد. اگر نیست، همین امروز ممنوعش کن (فصل ۲۷).

سؤالات مصاحبه (با پاسخ)

Junior — origin اسم خاصی است؟ قرارداد است؛ می‌تواند github باشد. فقط نام مستعار URL است.

Mid — چرا ff-only؟ جلوی mergeهای اتفاقی و تاریخچهٔ دندانه‌دار را می‌گیرد.

Senior — lease چه چیزی را می‌سنجد؟ هش refs/heads/... روی remote را با remote-tracking محلی مقایسه می‌کند.

✅ چک‌لیست فهم

  • fetch را بدون ترس می‌زنی
  • ahead/behind را می‌خوانی
  • -u عادت شده
  • force خام را کنار گذاشته‌ای

Senior — CODEOWNERS چگونه merge را قفل می‌کند؟ اگر Ruleset «Require review from Code Owners» روشن باشد، تغییر در مسیر بدون Approve مالک نمی‌آید.

✅ چک‌لیست فهم

  • ریپو با gh ساخته‌ای
  • README یک‌جمله‌ای + شروع سریع دارد
  • LICENSE و SECURITY وجود دارند
  • Topics تنظیم شده

Clone، Fork و Upstream — ورود به کد دیگران

Clone = کپی مخزن روی رایانهٔ تو (با تاریخچه). Fork = کپی مخزن زیر حساب GitHub خودت. PR را باید از fork خودت به مخزن اصلی بفرستی؛ اگر فقط clone کرده باشی و حق push نداشته باشی، PR ساخته نمی‌شود.

🎯 اهداف یادگیری

  • clone را با عمق و فیلتر درست انجام دهی
  • fork را با origin و upstream بچینی
  • شاخه را به‌روز نگه داری تا PR تمیز بماند

📥 clone

clone هوشمند
git clone git@github.com:rezaian-dev/javascript-persian-guide.git
git clone --depth 1 <url>              # فقط نوک — سریع، تاریخچه ناقص
git clone --filter=blob:none <url>     # partial؛ blob تنبل
gh repo clone rezaian-dev/javascript-persian-guide
🖥️ VS Code + GitHub
  1. Palette: Git: Clone یا Welcome → Clone Git Repository
  2. اگر افزونهٔ GitHub Pull Requests وصل است: Clone from GitHub و لیست ریپوهایت
  3. پوشه را انتخاب کن → Open
  4. Fork از Command Palette: GitHub Pull Requests: Fork
⌨️ Terminal

git clone git@github.com:org/repo.git gh repo clone org/repo gh repo fork org/repo --clone

depth 1 و بعدش

shallow clone برای CI عالی است. برای کار روزانه bisect و blame را ضعیف می‌کند. با git fetch --unshallow کاملش کن.

🍴 Fork — مدل مشارکت OSS

چیدمان استاندارد
gh repo fork rezaian-dev/javascript-persian-guide --clone=true
cd javascript-persian-guide
git remote -v
# origin    تو (fork)
# upstream  ریپوی اصلی

git fetch upstream
git switch main
git merge --ff-only upstream/main
git push origin main

قانون طلایی:

  • origin = ریپوی تو (حق push)
  • upstream = ریپوی صاحب پروژه (معمولاً read-only)
  • PR از origin/feat/x به upstream/main

در GitHub دکمهٔ Sync fork همین merge را گرافیکی می‌کند. در VS Code افزونهٔ PR ریموت‌ها را می‌شناسد.

🔁 مشارکت بدون fork — مدل تیمی

در سازمان، معمولاً مستقیم روی ریپو دسترسی write داری:

شاخه روی origin
git switch -c feat/docs origin/main
git push -u origin HEAD
gh pr create --base main

Fork برای OSS و پیمانکار خارجی است؛ برای همکار تمام‌وقت گام اضافه است.

سؤالات مصاحبه (با پاسخ)

Junior — فرق clone و download ZIP؟ ZIP بدون .git است؛ تاریخچه و شاخه ندارد.

Mid — چرا دو remote؟ تا بتوانی از upstream بگیر و به origin هل بدهی بدون حق نوشتن روی اصلی.

Senior — fork network چیست؟ گراف ریپوهای مشتق‌شده؛ GitHub objectها را تا حدی به اشتراک می‌گذارد. حذف fork تاریخچهٔ PR را پیچیده می‌کند.

✅ چک‌لیست فهم

  • clone با SSH انجام داده‌ای
  • origin/upstream را درست نام‌گذاری می‌کنی
  • Sync fork را قبل از PR تازه می‌زنی

Pull Request — دروازهٔ کیفیت تیم

Pull Request یعنی درخواست ادغام شاخهٔ تو در شاخهٔ هدف (معمولاً main). قبل از Merge، دیگران diff را می‌بینند، نظر می‌دهند و CI باید سبز باشد.

🎯 اهداف یادگیری

  • PR را با gh و از VS Code باز کنی
  • Draft، Checks و reviewers را درست به کار ببری
  • استراتژی merge را آگاهانه انتخاب کنی
  • PR بزرگ را بشکنی

شکل ۱۴ — Conversation، Files، Checks سبز، Able to merge.

📬 باز کردن PR

از ترمینال
git push -u origin HEAD
gh pr create --draft --fill --reviewer teammate
gh pr view --web
gh pr ready                 # از draft خارج شو
🖥️ افزونه GitHub Pull Requests
  1. بعد از Push، نوار آبی Create Pull Request
  2. یا Activity Bar → آیکون GitHub → Create Pull Request
  3. Draft را تیک بزن، Reviewer انتخاب کن
  4. Checkout روی PR دیگران برای تست محلی
  5. Files Changed → کامنت اینلاین → Submit Review
  6. Merge از همان پنل (Squash/Merge/Rebase طبق تنظیم تیم)
⌨️ Terminal + gh

git push -u origin HEAD gh pr create --draft --fill gh pr checkout 42 gh pr merge 42 --squash

بدنهٔ خوب:

  1. چرا این تغییر لازم است (لینک Issue)
  2. چه عوض شد — در سطح محصول نه خط‌به‌خط
  3. چگونه تست شد
  4. اسکرین شات اگر UI است
  5. ریسک و rollback
اندازه

هدف: زیر ۴۰۰ خط منطقی. اگر بزرگ است، stacked PR یا چند PR متوالی. ریویوکننده خسته Approve دروغین می‌زند.

🧪 Checks

هر Push روی شاخهٔ PR، Actions را آتش می‌زند (فصل ۲۸). مربع سبز Able to merge یعنی:

  • تعارض با base نیست
  • بررسی‌های required پاس شده
  • تعداد Approve کافی است
  • conversationها resolve شده‌اند (اگر اجباری باشد)

در VS Code تب Checks همان وضعیت را نشان می‌دهد.

🔀 سه دکمهٔ Merge

روش تاریخچهٔ main مناسب
Merge commit گره دووالدی حفظ PR به‌عنوان واحد
Squash یک کامیت شاخهٔ شلوغ / WIP زیاد
Rebase and merge خطی بدون گره merge تیم متعهد به کامیت تمیز

تیم باید یکی را قفل کند تا git log یک‌شکل بماند.

🧹 قبل از Review

تمیزکاری

git rebase origin/main          # روی شاخهٔ شخصی
git push --force-with-lease

تعارض را تو حل کن نه ریویوکننده.

PR به main مستقیم از لپ‌تاپ بدون CI

حتی در پروژهٔ شخصی Actions را روشن کن. حافظه عضله‌ای Production از همین‌جا ساخته می‌شود.

سؤالات مصاحبه (با پاسخ)

Junior — Draft یعنی چه؟ PR قابل merge نیست تا Ready شود؛ سیگنال «نگاه نکن هنوز».

Mid — چرا force-with-lease بعد از rebase؟ چون rebase هش عوض می‌کند؛ lease جلوی پاک کردن کار همکار روی همان شاخه را می‌گیرد.

Senior — stacked PR؟ زنجیرهٔ PR که هر کدام روی قبلی است؛ نیازمند ابزار (Graphite یا gh) و توافق تیم.

✅ چک‌لیست فهم

  • PR را با --draft باز می‌کنی
  • چرا را در بدنه می‌نویسی نه فقط چه
  • Checks را قبل از درخواست ریویو سبز می‌کنی
  • استراتژی merge تیم را می‌دانی

Code Review — فرهنگ، نه گیر دادن

Code Review یعنی قبل از Merge، حداقل یک نفر دیگر diff را بخواند. هدف پیدا کردن باگ و انتقال دانش است، نه خرد کردن نویسنده.

🎯 اهداف یادگیری

  • نظر را روی کد بگذاری نه روی آدم
  • از Prefixهای متعارف استفاده کنی
  • Review در VS Code را Submit کنی نه فقط کامنت محلی
  • بدانی Approve مسئولیت است

🧭 اصول

  1. نیت نویسنده را فرض خیر بگذار
  2. سؤال بپرس قبل از حکم («اینجا race ممکن است؟» نه «این غلط است»)
  3. nit را برچسب بزن تا با blocker قاطی نشود
  4. تحسین کن — الگوی خوب را تکرارپذیر کن
  5. خارج از scope را Issue کن نه گروگان PR

پیشوندهای رایج:

برچسب معنی
nit: سلیقه؛ اجباری نیست
suggestion: بهتر است
blocker: بدون این Merge نکن
question: نمی‌فهمم، توضیح بده
praise: این را بیشتر انجام بده

از ۲۰۲۵ Copilot Code Review هم نظر می‌دهد؛ آن را لایهٔ اول بدان نه جایگزین انسان. نظر AI را بدون خواندن Approve نکن.

🖱️ ریویو در VS Code

  1. PR را Checkout کن و واقعاً اجرا کن — نه فقط diff
  2. روی خط Add Comment — می‌توانی suggestion بگذاری (```suggestion)
  3. چند کامنت pending بمانند
  4. Submit Review با یکی از: Comment / Approve / Request Changes
کامنت بدون Submit

Pending فقط روی ماشین توست. نویسنده چیزی نمی‌بیند تا Submit کنی.

✅ چک‌لیست نویسنده قبل از درخواست ریویو

  • خودت diff را از بالا تا پایین خواندی
  • فایل debug و .env نیست
  • تست جدید برای رفتار جدید
  • CI سبز
  • توضیحات PR کامل است

✅ چک‌لیست ریویوکننده

  • صحت: آیا باگ منطقی هست؟
  • امنیت: تزریق، رمز، XSS، secret
  • طراحی: آیا API پایدار می‌ماند؟
  • تست: آیا فقدان پوشش هست؟
  • مشاهده‌پذیری: لاگ و خطا
سؤالات مصاحبه (با پاسخ)

Mid — Request Changes یعنی چه؟ Merge معمولاً قفل می‌شود تا همان نفر یا سیاست re-request برگردد.

Senior — LGTM بدون نگاه؟ بدهی اعتماد. در حادثه، امضای تو روی تاریخچه است. Ruleset «dismiss stale reviews» را روشن کن تا push جدید Approve کهنه را باطل کند.

✅ جمع‌بندی

ریویو مهارت اجتماعی + فنی است. ابزار را در فصل ۱۱ دیدی؛ فرهنگ را اینجا. بدون هر دو، CI فقط تئاتر است.

استراتژی شاخه — GitHub Flow تا Trunk-Based

استراتژی شاخه یعنی تیم توافق کند کد از کجا شروع شود، چطور به main برسد، و چه شاخه‌ای حق زنده ماندن طولانی دارد. شاخهٔ چند‌هفته‌ای با main واگرا می‌شود و merge را سخت می‌کند.

🎯 اهداف یادگیری

  • GitHub Flow را پیاده کنی
  • بدانی Git Flow کجا هنوز معنی دارد
  • Trunk-based و feature flag را توضیح دهی
  • سیاست شاخه را با Ruleset قفل کنی

شکل ۱۵ — شاخهٔ کوتاه از main، PR، CI، Review، Merge، Deploy.

🌊 GitHub Flow — پیش‌فرض این کتاب

  1. main همیشه قابل استقرار است
  2. شاخهٔ کوتاه‌عمر از main
  3. PR + Checks اجباری
  4. Merge → deploy خودکار
  5. اگر خراب شد: revert سریع نه freeze طولانی

مناسب وب، SaaS، اپ‌هایی با feature flag.

🌳 Git Flow — نسخه‌های سنگین

شاخه‌های develop، release/*، hotfix/*، main. برای نرم‌افزار با نسخهٔ شماره‌دار و چرخهٔ QA طولانی (امبدد، موبایل استور با ریویو یک‌هفته‌ای) هنوز زنده است. برای استارتاپ وب سربار است.

🚂 Trunk-Based

همه به main (trunk) با شاخه‌های چندساعته یا مستقیم. فیچر ناتمام پشت feature flag. نیاز به تست عالی و deploy ممتد دارد. گوگل و بسیاری از تیم‌های بزرگ این‌گونه‌اند.

مدل طول شاخه پیچیدگی سرعت تحویل
GitHub Flow روز کم بالا
Git Flow هفته زیاد متوسط
Trunk ساعت کم در Git، زیاد در flag خیلی بالا
شاخهٔ `feat/ali` سه‌ماهه

هر روز rebase سخت‌تر می‌شود. اگر کار بزرگ است، آن را پشت flag به main تکه‌تکه تحویل بده.

در VS Code git.branchProtection: ["main"] جلوی کامیت مستقیم را می‌گیرد — لایهٔ محلی قبل از Ruleset سرور.

سؤالات مصاحبه (با پاسخ)

Mid — چرا Git Flow با GitHub Actions درد دارد؟ چون دو شاخهٔ بلند باید همیشه همگام شوند؛ CI دوگانه و cherry-pick hotfix.

Senior — environment protection چگونه با Flow جور می‌شود؟ main → staging خودکار؛ production نیاز به Approve در Environment دارد نه شاخهٔ جداگانهٔ اجباری.

✅ چک‌لیست فهم

  • مدل تیم را در یک جمله می‌گویی
  • main را مقدس می‌دانی
  • شاخهٔ طولانی را بو می‌کشی

Rebase تعاملی — بازنویسی تاریخچه مثل مجسمه‌ساز

Rebase کامیت‌های شاخهٔ تو را برمی‌دارد و یکی‌یکی روی نوک یک شاخهٔ دیگر دوباره اعمال می‌کند. نتیجه تاریخچهٔ خطی است، ولی هش هر کامیت عوض می‌شود. فقط روی شاخه‌ای که دیگران از آن استفاده نمی‌کنند این کار را بکن.

🎯 اهداف یادگیری

  • rebase را به‌عنوان «کامیت‌ها را روی پایهٔ جدید دوباره پخش کن» توضیح دهی
  • rebase -i را برای squash و reword به کار ببری
  • --autosquash و fixup! را بلد باشی
  • قانون طلایی را هرگز نشکنی

شکل ۱۶ — rebase کامیت‌های جدید می‌سازد (D′ و E′)؛ هش عوض می‌شود.

🧠 rebase دقیقاً چه می‌کند؟

Git هر کامیت شاخهٔ تو را که در main نیست برمی‌دارد، main را HEAD می‌کند، و وصله‌ها را یکی‌یکی اعمال می‌کند. نتیجه: تاریخچهٔ خطی. هزینه: هویت جدید برای هر کامیت.

به‌روز کردن شاخهٔ شخصی
git fetch origin
git switch feat/auth
git rebase origin/main
git push --force-with-lease
🖥️ VS Code Git
  • ... → Pull (Rebase) برای به‌روز کردن شاخه
  • Palette: Git: Rebase Branch... → origin/main
  • تعارض: Merge Editor → Stage → Git: Rebase Continue
  • نوار زرد بالای ادیتور یعنی rebase ناتمام است — کامیت عادی نزن
  • Git: Rebase Abort برای پشیمانی
⌨️ Terminal

git fetch origin git rebase origin/main git rebase --continue git rebase --abort git push --force-with-lease

🎛️ interactive — اتاق عمل

پنج کامیت آخر را ویرایش کن
git rebase -i HEAD~5

هرگز rebase روی کامیت عمومی

اگر origin/main یا شاخه‌ای که همکارت checkout کرده شامل آن هش‌هاست، rebase = دو تاریخچهٔ موازی و force-push جنگی.

⚡ fixup و autosquash

بعد از ریویو، بدون کامیت «address comments»

--fixup پیامی مثل fixup! feat: add login form می‌سازد؛ autosquash آن را زیر هدف می‌چسباند. در Git جدید git commit --squash هم هست.

از Git ۲.۳۸+ پرچم --update-refs شاخه‌های محلی دیگری که به کامیت‌های بازنویسی‌شده اشاره می‌کردند را هم حرکت می‌دهد — نجات از شاخه‌های یتیم.

سؤالات مصاحبه (با پاسخ)

✅ چک‌لیست فهم

  • fixup + autosquash را بلدی
  • --abort عضله‌ای شده
  • force خام نمی‌زنی

Cherry-pick، revert پیشرفته و rerere

Cherry-pick یک کامیت مشخص را روی شاخهٔ فعلی کپی می‌کند (هش جدید). Revert یک کامیت خنثی‌کننده می‌سازد. rerere تعارضی را که قبلاً حل کرده‌ای به خاطر می‌سپارد.

🎯 اهداف یادگیری

  • cherry-pick را با درک هش جدید به کار ببری
  • revert یک merge را با -m درست انجام دهی
  • rerere را روشن کنی تا تعارض تکراری تکرار نشود
  • محدودهٔ کامیت (A..B) را در cherry-pick بفهمی

🍒 cherry-pick

وصلهٔ یک کامیت را روی HEAD فعلی اعمال می‌کند و کامیت تازه می‌سازد (هش متفاوت، معمولاً همان پیام).

یک هات‌فیکس را به main بیاور
git switch main
git cherry-pick 9f3a1c
git cherry-pick -x 9f3a1c          # در پیام: (cherry picked from ...)
git cherry-pick -n 9f3a1c          # بدون کامیت؛ فقط Index/Working
git cherry-pick feat/auth~3..feat/auth   # چند کامیت (بدون خود ~3)

در VS Code Graph: راست‌کلیک روی گره → Cherry Pick.

دو بار merge کردن همان منطق

اگر بعداً کل شاخه را merge کنی، cherry-pick قبلی ممکن است تعارض یا تکرار ایجاد کند. -x ردیابی را آسان می‌کند. برای جریان منظم، hotfix را روی main بزن و به شاخهٔ فیچر rebase کن.

↩️ revert merge

خنثی کردن PR ادغام‌شده
git revert -m 1 <merge-commit>
# -m 1 یعنی والد اول (معمولاً main) خط اصلی است

اگر دوباره همان شاخه را بخواهی merge کنی، Git فکر می‌کند تغییرات قبلاً آمده‌اند. راه‌حل رایج: revertِِ آن revert، یا rebase شاخه روی main جدید.

در GitHub دکمهٔ Revert روی PR ادغام‌شده یک PR معکوس می‌سازد — برای تیم‌ها امن‌تر از revert دستی.

🧠 rerere — Reuse Recorded Resolution

یک‌بار روشن کن، سال‌ها سود ببر
git config --global rerere.enabled true
git config --global rerere.autoUpdate true

وقتی تعارضی را حل می‌کنی، Git جفت «قبل/بعد» را ذخیره می‌کند. اگر همان تعارض در rebase بعدی آمد، خودش اعمال می‌کند.

بازرس
ls .git/rr-cache
git rerere diff
تیم‌های rebase-heavy

بدون rerere، هر rebase هفتگی همان تعارض CSS را دوباره حل می‌کنی. با rerere، ماشین حافظه می‌شود.

🎯 محدوده و خالی

git cherry-pick --empty=drop در Git جدید کامیت‌هایی که بعد از اعمال خالی‌اند را رد می‌کند. برای picking بازه روی شاخهٔ تقریباً همگام مفید است.

سؤالات مصاحبه (با پاسخ)

Junior — cherry-pick کپی است؟ کپی تغییر است نه کپی شیء؛ کامیت جدید با والد جدید.

Mid — چرا -m 1؟ merge دو درخت والد دارد؛ باید بگویی نسبت به کدام diff را معکوس کنیم.

Senior — rerere با conflict style diff3؟ پیش‌نمایش غنی‌تر است؛ حافظهٔ rerere روی نتیجهٔ staged کار می‌کند نه روی نشانه‌های فایل.

✅ چک‌لیست فهم

  • یک cherry-pick با -x زده‌ای
  • revert merge را فهمیده‌ای
  • rerere جهانی روشن است

Hooks و کیفیت کامیت — lint قبل از push

Hook اسکریپتی است که Git در لحظه‌های مشخص (مثلاً قبل از commit) اجرا می‌کند. اگر اسکریپت با خطا خارج شود، آن commit یا push انجام نمی‌شود.

🎯 اهداف یادگیری

  • hook محلی را از hook سمت سرور جدا کنی
  • بدانی .git/hooks پوشیدنی نیست
  • Husky / pre-commit framework را برای تیم بچینی
  • محدودیت hook را بشناسی (قابل دور زدن است)

🪝 Git hooks کجایند؟

.git/hooks/ نمونه‌های *.sample دارد. فعال‌سازی = حذف پسوند و اجرایی کردن.

pre-commit ساده — تست‌شده
cat > .git/hooks/pre-commit << 'EOF'
#!/usr/bin/env bash
set -euo pipefail
files=$(git diff --cached --name-only || true)
if printf '%s\n' "$files" | grep -Eq '(^|/)\.env$'; then
  echo "do not commit .env" >&2
  exit 1
fi
exit 0
EOF
chmod +x .git/hooks/pre-commit
`set -e` و grep

اگر بنویسی echo "$files" | grep ... && exit 1 بدون if، وقتی .env در stage نیست grep کد ۱ برمی‌گرداند و set -e کل هوک را شکست می‌دهد — یعنی هیچ کامیتی رد نمی‌شود. الگوی if grep; then exit 1; fi را استفاده کن.

مشکل: این فایل در مخزن نیست. همکار تو hook ندارد.

هویت و راز — امضا، 2FA، passkey و secret

امضای کامیت ثابت می‌کند این شیء با کلید ثبت‌شدهٔ تو ساخته شده. 2FA جلوی ورود با رمز تنها به حساب GitHub را می‌گیرد. secretهای لو رفته را git rm پاک نمی‌کند — در تاریخچه می‌مانند.

🎯 اهداف یادگیری

  • کامیت Signed و Verified را از هم تشخیص دهی
  • 2FA و passkey را روی حساب GitHub اجباری کنی
  • PAT، SSH و GitHub App را مقایسه کنی
  • secret را از تاریخچه پاک کنی اگر فاجعه شد

✅ Verified یعنی چه؟

GitHub کامیت را Verified می‌گذارد اگر:

  1. با کلید ثبت‌شده (SSH یا GPG یا S/MIME) امضا شده باشد
  2. نویسنده با حساب منطبق باشد

در فصل ۲ SSH signing را چیدیم. برای تگ انتشار:

تگ امضاشده

git push origin v1.0.0

Ruleset می‌تواند Require signed commits را روی main اجباری کند.

🔐 حساب GitHub در ۲۰۲۶

حداقل‌ها:

  • Passkey / 2FA اجباری برای orgهای جدی
  • Sudo mode برای کارهای حساس
  • Session را در دستگاه عمومی قطع کن
  • SSH keys را سالی یک‌بار مرور کن
  • Authorized applications OAuth را هرس کن

Rulesets — سیاست شاخه در سطح سازمان

Ruleset مجموعهٔ قوانین روی شاخه است — مثلاً push مستقیم به main ممنوع، CI باید سبز باشد، Merge فقط بعد از Approve. از Branch Protection قدیمی کامل‌تر است.

🎯 اهداف یادگیری

  • Ruleset را به‌جای یک تیک ساده طراحی کنی
  • required checks، review و linear history را قفل کنی
  • Environments را برای production بفهمی
  • CODEOWNERS را به سیاست وصل کنی

🧱 چرا Rulesets؟

Branch protection Rulesets
تعداد سیاست یکی per branch چند لایه قابل‌ترکیب
هدف نام شاخه الگو (release/**) + tagging

سازمان محدود ارث‌بری Enterprise → Org → Repo
ارزیابی — تاریخچهٔ ارزیابی و بینش

حداقل سیاست main در ۲۰۲۶:

  1. Restrict deletions
  2. Block force pushes
  3. Require a pull request (۱–۲ Approve)
  4. Require status checks to pass (CI)
  5. Require conversation resolution
  6. Require signed commits (اگر تیم آماده است)
  7. Dismiss stale reviews on new push
  8. Require review from Code Owners

v* را قفل کن تا کسی تگ نسخه را جابه‌جا نکند. همراه Immutable Releases، عرضه قابل‌اثبات می‌شود.

Senior — bypass چه کسی باید داشته باشد؟ فقط bot حادثه و چند admin. اگر همه bypass دارند، سیاست تئاتر است.

✅ چک‌لیست فهم

  • force push روی main بسته است
  • CI required است نه تزئینی
  • production Environment Approve دارد
  • CODEOWNERS زنده است

GitHub Actions — از رویداد تا استقرار

GitHub Actions یعنی با هر رویداد (مثلاً push یا PR) یک گردش‌کار YAML روی سرور GitHub اجرا شود: تست، lint، ساخت. Secret را در مخزن ذخیره می‌کنی نه داخل کد.

🎯 اهداف یادگیری

  • workflow، job، step و runner را جدا کنی
  • CI را روی PR اجباری کنی
  • secret را از Environment بخوانی نه از لاگ
  • OIDC را به‌جای Access Key ابری ترجیح دهی

شکل ۱۷ — Event → Workflow → Jobs موازی → Checks → Merge/Deploy.

شکل ۱۸ — صفحهٔ run: جاب‌های lint/test/build و لاگ سبز.

📄 اولین workflow

.github/workflows/ci.yml
name: CI
on:
  pull_request:
  push:
    branches: [main]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.13"
      - run: pip install -r src/requirements.txt
      - run: python src/build.py --html

قواعد:

  • pin اکشن‌ها حداقل روی major (@v4)؛ برای عرضهٔ حساس روی SHA
  • pull_request از fork به secretهای مخزن دسترسی ندارد (امنیت)
  • concurrency را برای لغو runهای کهنه روی همان شاخه بگذار

♻️ Reusable و matrix

از ۲۰۲۵ می‌توان workflowهای reusable را تو در تو صدا زد (تا سقف مستند GitHub). ماتریس برای چند نسخهٔ Node/Python:

✅ چک‌لیست فهم

داخلی Git — packfile، gc، fsck و reftable

Git فایل‌ها را اول جدا و بعد فشرده در packfile نگه می‌دارد. gc زباله‌ها را جمع می‌کند. این فصل وقتی لازم می‌شود که مخزن باد کرده یا fsck خطا می‌دهد.

🎯 اهداف یادگیری

  • loose object را از packfile تشخیص دهی
  • gc و repack را با احتیاط اجرا کنی
  • fsck را برای سلامت دیتابیس به کار ببری
  • reftable را به‌عنوان backend مدرن refs بشناسی

🗄️ objects

دو شکل:

  • Loose: .git/objects/ab/cdef... یک فایل per شیء
  • Packed: pack-....pack + .idx — دلتا فشرده، سریع برای fetch
نگاه
git count-objects -vH
git verify-pack -v .git/objects/pack/*.idx | sort -k 3 -n | tail
git cat-file -t 9f3a1c
git cat-file -s 9f3a1c

git gc looseها را pack می‌کند، unreachable را بعد از grace period دور می‌ریزد. git gc --prune=now تهاجمی است.

gc وسط کار دیگران

روی سرور شلوغ gc را در maintenance پنجره بزن. git maintenance start زمان‌بندی امن‌تری است.

🔗 refs: files در برابر reftable

سنت: هر شاخه یک فایل در .git/refs/heads + packed-refs. با صدها هزار ref (Gerrit، monorepo) کند می‌شود.

مخزن آزمایشی
git init --ref-format=reftable /tmp/rt

Reftable در مسیر Git ۳.۰ production-ready است. GitHub در مقیاس خودش از سیستم‌های مشابه بهره می‌برد. برای پروژهٔ معمولی files کافی است.

🩺 fsck و recover

سلامت
git fsck --full
git fsck --lost-found

dangling commit اغلب کامیت‌های rebaseشده‌اند — گاهی نجات با git show <hash> و شاخه ساختن.

اگر index.lock ماند (کریش VS Code): فقط وقتی هیچ فرایند Git/Code روی مخزن نیست حذفش کن.

🧹 تاریخچهٔ سنگین

چه چیزی حجم را خورده؟
git rev-list --objects --all \
  | git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' \
  | awk '/^blob/' | sort -k3 -n | tail

بعد git filter-repo برای حذف باینری accidental. همه باید re-clone کنند.

سؤالات مصاحبه (با پاسخ)

Mid — چرا clone دوم سریع‌تر است؟ pack از قبل دلتا شده؛ looseها در مسیر critical نیستند.

Senior — unreachable چه زمانی می‌میرد؟ reflog expire (پیش‌فرض ~90 روز) بعد prune. تا آن موقع reset --hard قابل برگشت است.

✅ چک‌لیست فهم

  • count-objects -vH را خوانده‌ای
  • می‌دانی gc unreachable را بعد از reflog می‌کشد
  • reftable را با SHA-256 قاطی نمی‌کنی (دو محور جدا)

مخازن بزرگ — partial clone، Scalar و monorepo

در مخزن خیلی بزرگ، کل تاریخچه و همهٔ فایل‌ها را یکجا clone نکن. Partial clone محتوا را تنبلانه می‌آورد؛ sparse-checkout فقط پوشه‌های لازم را روی دیسک می‌گذارد.

🎯 اهداف یادگیری

  • partial clone و sparse-checkout را ترکیب کنی
  • LFS را از partial clone جدا کنی
  • بدان کی monorepo و کی polyrepo
  • Scalar و Git protocol v2 را بشناسی

🧊 Partial clone

بدون همهٔ blobها
git clone --filter=blob:none git@github.com:org/mono.git
git clone --filter=tree:0 <url>     # حتی تنبل‌تر؛ treeها هم بعداً

وقتی فایل را checkout می‌کنی Git blob را می‌گیرد. نیاز به پروتکل v2 و سرور پشتیبان (GitHub دارد).

📂 Sparse checkout cone

فقط دنیای خودت
git sparse-checkout init --cone
git sparse-checkout set apps/web packages/ui

--cone الگوهای پوشه‌ای سریع‌تر از globهای پراکنده است.

🧰 Scalar

ابزار مایکروسافت (همراه Git for Windows / قابل نصب جدا): git maintenance، fsmonitor، partial clone را یک‌جا برای ریپوهای عظیم ویندوز تنظیم می‌کند. اگر checkout ۳۰ ثانیه طول می‌کشد، Scalar را امتحان کن نه «لپ‌تاپ نو».

🏢 Monorepo در برابر Polyrepo

Monorepo Polyrepo
تغییر چندپروژه یک PR چند PR هماهنگ
CI باید path filter شود وگرنه می‌سوزد
دسترسی همه همه‌چیز را می‌بینند مگر sparse/server راحت‌تر per-team
ابزار Nx, Bazel, Turborepo Actions ساده
path filter در Actions

سؤالات مصاحبه (با پاسخ)

Senior — blob:none در برابر LFS؟ LFS باینریهای مشخص را خارج می‌کند. Partial clone همهٔ blobهای Git را تنبل می‌کند. اغلب با هم استفاده می‌شوند.

✅ چک‌لیست فهم

  • clone فیلترشده را تجربه کرده‌ای
  • CI را path-aware کرده‌ای
  • می‌دانی monorepo بدون ابزار ساخت جهنم است

۲۰ اشتباه رایج و راه‌حل

بیست اشتباه رایج (از add . کور تا force روی main) و برای هر کدام همان Undo مشخص. قبل از کپی فرمان، ستون «چه‌کار نکن» را بخوان.

🎯 اهداف یادگیری

  • اشتباه را نام ببری قبل از اینکه فاجعه شود
  • راه‌حل درست را از راه‌حل خطرناک جدا کنی

💣 لیست

  1. git add . کور: .env و dist می‌آید. راه‌حل: -p و gitignore.
  2. کامیت روی main: Ruleset + branchProtection در VS Code.
  3. پیام update: Conventional.
  4. amend بعد از push: revert یا کامیت جدید.
  5. --force به origin/main: lease + ممنوعیت سرور.
  6. rebase شاخهٔ مشترک: merge یا revert.
  7. Discard در VS Code بدون Timeline: Local History را فوراً چک کن.
  8. clone با HTTPS و بعداً گیر token: remote را به SSH عوض کن.
  9. ignore کردن فایل trackشده: rm --cached.
  10. حل تعارض با Accept Both کور: تست.
  11. PR ۵۰۰۰ خطی: بشکن.
  12. Approve بدون اجرای کد: حداقل تست CI اجباری.
  13. secret در پیام کامیت: revoke.
  14. submodule فراموش‌شده: clone --recurse-submodules (اگر تیم submodule دارد؛ وگرنه اجتناب).
  15. نام شاخه با فاصله: از / و -.
  16. کشیدن ZIP به‌جای clone: تاریخچه نداری.
  17. دو نفر یک worktree/شاخه: قفل Git.
  18. اعتماد به Smart Commit: خاموشش کن.
  19. اکشن @main: pin.
  20. فکر کردن که GitHub = بکاپ تنها: remote دوم یا mirror برای چیزهای حیاتی.

مصاحبه، واژه‌نامه و نقشه راه بعد از کتاب

پرسش‌های مصاحبه با جواب کوتاه، جدول واژهٔ فارسی/انگلیسی، و مسیر بعد از کتاب. اگر بتوانی سه درخت و DAG را روی کاغذ بکشی، بیشتر سؤال‌ها همان مدل‌اند.

🎯 اهداف یادگیری

  • به پرسش‌های سطح‌بندی‌شده با مدل سه‌درخت جواب بدهی
  • اصطلاح انگلیسی را با معادل دقیق فارسی بگویی
  • مسیر یادگیری بعد از این مرجع را بدانی

🎤 پرسش‌های مصاحبه (با پاسخ کوتاه)

Junior

  • Git چیست؟ سیستم نسخه‌بندی توزیع‌شده مبتنی بر snapshot و محتوا-آدرس.
  • staging یعنی چه؟ پیش‌نویس کامیت؛ Index.
  • تفاوت clone و fork؟ clone محلی است؛ fork کپی حساب‌محور روی GitHub.
  • pull در برابر fetch؟ pull = fetch + ادغام/rebase.

Mid

  • merge در برابر rebase؟ حفظ گره در برابر بازنویسی خطی؛ rebase فقط روی شاخهٔ شخصی.
  • reset --soft/--mixed/--hard؟ کدام درخت‌ها حرکت می‌کنند (فصل ۸).
  • A...B در diff؟ از جد مشترک؛ همان نمای PR.
  • چرا commit amend هش را عوض می‌کند؟ هویت شیء از محتواست.
  • force-with-lease چیست؟ force مشروط به نخوردن کار دیگران.

Senior / Staff

  • DAG و چرا مهم است؟ توپولوژی تاریخچه؛ merge دو والد، rebase گره جدید.
  • revert یک merge؟ -m 1 و پیامد merge دوباره.
  • Ruleset در برابر branch protection؟ لایه‌بندی، الگو، bypass، ارث سازمانی.
  • OIDC در Actions؟ هویت کوتاه‌عمر به ابر بدون کلید ماندگار.
  • چگونه باگ را در ۱۰ هزار کامیت پیدا می‌کنی؟ bisect run + تست قطعی.
  • monorepo در Git چگونه زنده می‌ماند؟ partial clone، sparse cone، path-filter CI، گاهی Scalar.
  • PR عامل AI را چطور کنترل می‌کنی؟ draft، required review غیرنویسنده، دستورالعمل، CI بعد از Approve.
